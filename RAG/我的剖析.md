> ### 2. 这些上下文是怎么被检索出来的？
>
> 在执行 `run_rag_pipline(query, query, k=3)` 时，内部执行了标准的 **向量相似度检索（Similarity Search）**：
>
> ```python
> # 1. 把 query 文本通过百炼 embedding 模型转化为 1536 维向量
> 
> # 2. Chroma 在 zhidu_db_bailian 集合中计算向量余弦相似度
> 
> related_docs = zhidu_db.similarity_search("那个，我们公司有什么规定来着？", k=3)
> 
> 
> 
> # 3. 将检索到的 top 3 个 chunk 拼接成 context 字符串
> 
> context = "\n".join([f"上下文{i+1}: {doc.page_content} \n" for i, doc in enumerate(related_docs)])
> ```
>

> - 因此百炼 Embedding 向量计算后，这 3 个切片与 Query 的余弦相似度最高（Top 3），被选出并拼接作为上下文喂给大模型。



> ⭐**第二种写法的上下文是哪来的？**
>
> 
>
> 这次的执行过程展示了 RAG 中 **`query2doc`（伪文档扩展 / 查询扩展）技术** 的实际运作机制。
>
> 我们可以将整个过程拆解为三个阶段来看：
>
> ---
>
> ### 一、`query2doc` 做了什么？
>
> `query2doc`（Query to Pseudo-Document）是一种**查询扩展技术**。它的核心逻辑是：
> 1. 原问题 `"那个，我们公司有什么规定来着？"` 过于简短、泛化，缺乏具体的检索关键词。
> 2. 于是先让 LLM 自行“脑补/拓展”一段包含常见公司制度的**伪文档（Pseudo-Doc）**：
>    > `公司规定较多，主要包括：考勤打卡、请假审批、薪酬保密、报销流程、保密义务、廉洁合规、办公纪律、奖惩制度等。具体想了解哪一项？`
> 3. 将 **原问题 + 伪文档** 拼接在一起，组成信息量更丰富的 `context_query` 去向量数据库中进行检索。
>
> ---
>
> ### 二、为什么召回的上下文（Context）变了？
>
> 由于扩展后的检索文本中引入了 **“考勤打卡”**、**“奖惩制度”**、**“办公纪律”** 等具体领域词汇，Chroma 数据库的向量相似度计算被引导到了包含这些词的具体条款上：
>
> | 召回上下文   | 对应切片                                                     | 为什么被召回（命中哪些扩展词）                   |
> | :----------- | :----------------------------------------------------------- | :----------------------------------------------- |
> | **上下文 1** | **Chunk #03** (`第二节考勤规定`)                             | 命中 **“考勤”**                                  |
> | **上下文 2** | **Chunk #09** (`。5、考勤员徇私舞弊、弄虚作假的，按学校奖惩规定处理...`) | 命中 **“考勤”**、**“奖惩制度”**                  |
> | **上下文 3** | **Chunk #25** (`第五节违规违纪处理 1. 迟到、早退...每次扣减工资50元...`) | 命中 **“考勤打卡”**、**“纪律/违规”**、**“处罚”** |
>
> > 💡 **对比直接使用 `query` 检索**：之前只召回了泛化的“企业文化口号”和两节标题；而加入 `query2doc` 后，成功精准召回了包含“违规违纪处罚与考勤扣款”的具体细则切片。
>
> ---
>
> ### 三、为什么 LLM 最终还是回答“不知道”？
>
> 虽然召回的内容更精准了，但最终 LLM 的判定逻辑如下：
>
> 1. **Prompt 的硬性限制**：
>    ```text
>    如果上下文信息context没有和问题相关的信息，请直接先回答不知道
>    ```
> 2. **输入与上下文的冲突**：
>    - 用户给 LLM 的输入问题依然是原始的全局性大问题：`"那个，我们公司有什么规定来着？"`
>    - 而此时传入的上下文只有 3 条细枝末节的片段（一条考勤员舞弊处罚、一条迟到早退扣款 50 元）。
> 3. **LLM 的拒绝回答机制（Anti-Hallucination）**：
>    - LLM 发现这 3 条上下文远远不足以回答“公司整体有什么规定”，在 Prompt 的严格约束下，它不能自行胡编乱造，因此严格遵守指令回答：**“不知道。您的问题太宽泛了，没有具体说明想了解哪方面的规定……”** 并引导用户提供更具体的提问。



#### HyDE

- 利用大语言模型生成伪文档embedding



~~~python
from langchain.chains import HypotheticalDocumentEmbedder, LLMChain
from langchain.prompts import PromptTemplatefrom langchain.chains import HypotheticalDocumentEmbedder, LLMChain
from langchain.prompts import PromptTemplate

def hyde(query, include_query=True):
    prompt_template = """你是一名公司员工制度的问答助手, 熟悉公司规章制度，请简短回答以下问题:
    Question: {question}
    Answer:"""
    
    prompt = PromptTemplate(input_variables=["question"], template=prompt_template)
    # llm_chain = LLMChain(llm=langchain_llm, prompt=prompt)
    # 关键修改：用 prompt | langchain_llm 替代 LLMChain
    llm_chain = prompt | langchain_llm

    embeddings = HypotheticalDocumentEmbedder(llm_chain=llm_chain,
                                base_embeddings=embedding)
    hyde_embeddings = embeddings.embed_query(query)
    
    if include_query:
        query_embeddings = embedding.embed_query(query)
        result = (np.array(query_embeddings) + np.array(hyde_embeddings)) / 2
        result = list(result)
    else:
        result = hyde_embeddings
    result = list(map(float, result))
    return result
    
query = "那个，我们公司有什么规定来着？"

run_rag_pipline(query, hyde(query), k=3, context_query_type="vector")

run_rag_pipline(query, hyde(query, include_query=False), k=3, context_query_type="vector")
~~~

> ⭐⭐**两者区别是什么？**
>
> 
>
> 这两次调用的核心区别在于：**检索时使用的向量是否混入了用户原始 Query 的向量**。
>
> 代码中的逻辑是：
> * `include_query=True`（默认）：向量为 `(原 Query 向量 + HyDE 伪文档向量) / 2`（**混合向量**）
> * `include_query=False`：向量仅为 `HyDE 伪文档向量`（**纯伪文档向量**）
>
> ---
>
> ### 1. 召回上下文的本质差异
>
> | 对比项           | 第一次：`include_query=True`（混合向量）             | 第二次：`include_query=False`（纯 HyDE 向量）                |
> | :--------------- | :--------------------------------------------------- | :----------------------------------------------------------- |
> | **检索向量来源** | 原提问向量 + 伪文档向量 取平均                       | 仅使用大模型生成的伪文档向量                                 |
> | **召回的上下文** | 召回了比较零碎的片段（企业文化、考勤标题、加班标题） | 召回了极其精准的制度总览（**第一节适用范围：本制度包括了考勤、休假、加班等**；第五节违规违纪处理等） |
> | **最终回答效果** | 模型认为上下文太碎片，“不知道具体指哪项”             | 模型根据召回的《适用范围》和《违规处理》，**给出了结构完整、条理清晰的正面回答** |
>
> ---
>
> ### 2. 为什么在这次查询中 `include_query=False` 效果反而更好？
>
> 用户的问题是：
> > **`"那个，我们公司有什么规定来着？"`**
>
> 这是一个典型的 **短文本、高度口语化、模糊含糊** 的 Query（包含“那个”、“来着”等口头助词）。
>
> 1. **混合原始 Query 时（`include_query=True`）**：
>    * 原始 Query 过于口语和模糊，它的向量表征带有很强的模糊性与口语噪音。
>    * 当把它与 HyDE 向量按 `50% : 50%` 平均后，原本精准的伪文档向量被原始 Query 的口语噪音**向后拉偏**了。
>    * 导致最终只召回了一些边缘片段（如企业文化宣传语），缺少关于“公司制度概览”的核心条款。
>
> 2. **纯使用 HyDE 时（`include_query=False`）**：
>    * HyDE 的 Prompt 是：*“你是一名公司员工制度助手，请简短回答...”*。
>    * 大模型先脑补生成了一段规范的书面语伪文档（例如：*“公司制度包括考勤制度、请假制度、休假规定、违规违纪处理等...”*）。
>    * 纯用这段**书面化、充满规章制度专业词汇的假定文档**去匹配 Chroma 数据库中的真文档，实现了从 **`Query - Doc 匹配`** 到 **`Doc - Doc 匹配`** 的跨越。
>    * 因而精确命中了文档中写有 *“本制度包括了考勤、休假、加班等方面的规定”* 的**总述段落**（上下文2），让 RAG 最终成功回答。
>
> ---
>
> ### 总结与工程经验
>
> * **HyDE 的优势**：消除了“用户口语化提问”与“知识库书面语文档”之间的**表达鸿沟（Semantic Gap）**。
> * **何时混合 Query (`include_query=True`)**：
>   当用户问题中包含**非常明确的实体、型号、专有名词、特定人名**时，保留原 Query 向量能防止大模型“脑补伪文档”时产生幻觉偏离主题。
> * **何时纯用 HyDE (`include_query=False`)**：
>   当用户提问**极度简短、口语化、含糊抽象**时（如本例），纯 HyDE 向量能过滤口语噪音，大幅提升文档召回质量。

>
> 这是一个非常核心而且容易让人误解的概念。
>
> 一句话回答：
> **原始的文本 Query（字符串）本身完全没有被修改！被改变的是去向量数据库里“找资料时用的数学向量（Embedding）”。**
>
> 为了让你彻底明白，我们可以把整个过程拆解开来看：
>
> ---
>
> ### 1. 文本层面：Query 从始至终没有变
>
> 无论 `include_query` 是 `True` 还是 `False`：
> * 传给最后大模型回答的 Prompt 里，`{question}` 永远是你的原话：
>   > **`"那个，我们公司有什么规定来着？"`**
> * 大模型在最后生成答案时，依然是在回答你这个原汁原味的问题。
>
> ---
>
> ### 2. 向量检索层面：它在数据库眼里“变成了什么”？
>
> 虽然原始文字没变，但在**送入向量数据库去搜索相关文档**的那一刻，代表这个 Query 的**向量形态**发生了改变：
>
> #### ① 当 `include_query=False` 时：
> 大模型先“脑补”生成了一段书面伪文档（Hypothetical Document），比如：
> > **伪文档文本**：*“公司的具体规定通常包括：员工考勤打卡制度、日常请假与休假规定、加班与调休管理办法、违规违纪处罚条例以及保密制度等。”*
>
> * **在数据库眼里的 Query**：
>   数据库**完全不看**你原本那句口语 `"那个，我们公司有什么规定来着？"`，它接收到的检索向量，**100% 是上面那段书面伪文档的向量**。
> * **相当于在语义上把 Query “翻译”成了**：
>   > *“员工考勤打卡制度、日常请假与休假规定、加班与调休管理办法、违纪处罚条例……”*
>
> ---
>
> #### ② 当 `include_query=True` 时：
> 它同时计算了两个向量：
> 1. 原提问向量：`V_原问题 = Embedding("那个，我们公司有什么规定来着？")`
> 2. 伪文档向量：`V_伪文档 = Embedding("公司的具体规定通常包括：员工考勤打卡...")`
> 3. 最终检索向量：`V_检索 = (V_原问题 + V_伪文档) / 2`
>
> * **在数据库眼里的 Query**：
>   它处于**口语闲聊提问**与**专业规章文档**的**“正中间”**（50% 语义来自口语原提问，50% 语义来自大模型脑补的书面伪文档）。
>
> ---
>
> ### 3. 一张图对比普通检索、Query2Doc 与 HyDE
>
> 你笔记本前面学过 `query2doc`，把它们放一起对比就会彻底清晰：
>
> | 检索方式           | 文本（Query）被改成什么样？                                  | 向量数据库实际用来比对的向量                                 |
> | :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **传统检索**       | `"那个，我们公司有什么规定来着？"`（没改）                   | `Embedding(原问题)`                                          |
> | **Query2Doc**      | **直接把文本拼长了**：<br>`"那个，我们公司有什么规定来着？，公司规定包括考勤、休假、加班..."` | `Embedding(拼接后的长文本)`                                  |
> | **HyDE (`False`)** | 文本没改，但生成了假想伪文档                                 | **`Embedding(假想伪文档)`**<br>*(完全用假想答案去搜真实答案)* |
> | **HyDE (`True`)**  | 文本没改，但生成了假想伪文档                                 | **`50% Embedding(原问题) + 50% Embedding(假想伪文档)`**<br>*(在向量空间里把两者融合)* |
>
> ### 总结
> * **Query 字符串本身没变**，用户问什么最后答什么；
> * `include_query=False` 相当于告诉向量数据库：**“别管用户问得多模糊口语，直接拿着大模型脑补的书面制度概要去库里捞书面文档”**；
> * `include_query=True` 相当于告诉向量数据库：**“既要参考大模型脑补的内容，也要兼顾用户原本口头提问的倾向”**。



#### 总结query2doc和HyDE

> ⭐**其实Query2Doc 与 HyDE都是在优化用户提问时的问题，对吗？**
>
> 
>
> **完全正确！你的理解一针见血。**
>
> 在 RAG 架构的分类中，**Query2Doc** 和 **HyDE** 都属于同一个技术分支：**“检索前查询增强与改写”（Pre-Retrieval / Query Transformation）**。
>
> 它们的本质目的完全相同，都是为了解决 RAG 检索中著名的 **“语义鸿沟”（Semantic Gap）**：
>
> ---
>
> ### 1. 它们试图解决的共同痛点
>
> 用户在提问时，经常存在两个天然问题：
> 1. **口语化与碎片化**：用户提问往往很短、很碎（比如 *“那个，怎么报销来着？”*）；
> 2. **提问与文档的表达不一致**：
>    * 用户输入的是**“疑问句”**（*“感冒发烧去出差怎么请假？”*）；
>    * 知识库里存的是**“陈述句/制度条款”**（*“第三节：教职工病假需在两个工作日内补办手续...”*）。
>
> 在传统的向量检索中，拿“短小的疑问句”去匹配“大篇幅的书面陈述句”，向量相似度往往很低。所以，它们都在**想办法把用户的提问“改写/扩写”成更像知识库文档的形式**。
>
> ---
>
> ### 2. 两者的实现手段有何不同？
>
> 虽然目标一致，但它们的**实现思路（路径）**不同：
>
> ```
>                     ┌─► Query2Doc:【文本拼接】──► 拼成更长的字符串 ──► 生成一个混合向量
>                     │
> 用户原始提问 ───────┤
>                     │
>                     └─► HyDE:     【向量对齐】──► 分别转成数学向量 ──► 在向量空间中融合
> ```
>
> | 对比维度     | **Query2Doc**                                                | **HyDE**                                                     |
> | :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **所属层面** | **文本级改写（Text-level）**                                 | **向量级对齐（Embedding-level）**                            |
> | **做法**     | 大模型生成补充信息后，**直接用字符串拼在原问题后面**：<br>`f"{query}, {doc_info}"` | 大模型生成伪文档后，**分别对原问题和伪文档算向量**，在数学空间里取平均或直接替换。 |
> | **核心哲学** | “既然原问题太短，我就多补点相关词和上下文，让字数变多、信息更丰富。” | “不要拿【问题】搜【答案】；先让大模型造个【假答案】，拿【假答案】搜【真答案】（Doc-Doc 匹配）。” |
>
> ---
>
> ### 3. 拓展：在整个 RAG 体系里的全貌
>
> 你在这一章学到的很多技巧，其实都是在**“优化用户问题”**这个预处理阶段发力：
>
> * **HyDE / Query2Doc**：把“口语提问”扩写成“书面伪文档”（解决口语与书面语的差异）；
> * **Query Rewrite（查询改写）**：去除多轮对话里的代词（比如把“它多少钱？”改写为“iPhone 15 多少钱？”）；
> * **Sub-Question（子问题拆解）**：把复杂的长问题拆成若干个简单小问题分别检索；
> * **Step-back Prompting（后退一步提问）**：把具体狭窄的问题提升到更高维度的概念去检索。
>
> 所以你的直觉非常准，不管是直接拼文字（Query2Doc）还是在向量层面做融合（HyDE），**都是在利用大模型给原始问题“加Buff”，让检索器更容易在知识库中搜中正确内容。**



> ⭐⭐**“生成一个混合向量”和“在向量空间中融合”的区别是什么？**
>
> 
>
> 这两个表述看似相似，但在计算机和数学底层，是 **两种完全不同的“融合阶段”与“融合方式”**：
>
> * **Query2Doc（“生成一个混合向量”）**：是 **先混文字，再算向量** —— 属于 **“早期融合（Early Fusion）”**。
> * **HyDE（“在向量空间中融合”）**：是 **先各自算向量，再在数学空间中叠加** —— 属于 **“晚期融合（Late Fusion）”**。
>
> 我们可以从以下三个维度彻底看清它们的区别：
>
> ---
>
> ### 1. 计算过程的区别（核心差别）
>
> #### ① Query2Doc（文本混合 ➔ 端到端生成向量）
> $$V = \text{Embedding}(\text{原问题} + \text{伪文档})$$
> * **过程**：先把原问题和伪文档用字符串硬拼成一段长文本：
>   `"那个，我们公司有什么规定来着？, 公司的规章制度包括..."`
> * 然后把这一整段长文本**一次性喂给 Embedding 模型**（通常是 Transformer 架构）。
> * 在模型内部，Transformer 的 **Self-Attention（自注意力机制）** 会让原问题的每一个字和伪文档的每一个字**进行深度的非线性交叉计算**，最后端到端输出**一个**全新的向量。
>
> #### ② HyDE（各自独立编码 ➔ 向量空间几何运算）
> $$V = \frac{\text{Embedding}(\text{原问题}) + \text{Embedding}(\text{伪文档})}{2}$$
> * **过程**：原问题和伪文档**互不见面、互不影响**。
> * 原问题单独进模型，算出一个坐标 $V_A$；
> * 伪文档单独进模型，算出一个坐标 $V_B$；
> * 最后在由几千个维度组成的高维几何空间（向量空间）中，通过纯粹的高中数学向量加法和标量除法，求出这两个坐标的**中点坐标**。
>
> ---
>
> ### 2. 生动比喻：做菜 vs 调鸡尾酒
>
> * **Query2Doc（先拼文本）** 就像 **把两种食材扔进搅拌机一起打碎烹饪**：
>   原问题和伪文档在模型内部充分发生了“化学反应”（自注意力计算），你很难再单独把原问题剥离出来。
> * **HyDE（空间融合）** 就像 **调鸡尾酒**：
>   原问题是一杯伏特加，伪文档是一杯果汁，它们各自是独立的成品，最后在杯子里按照 50% : 50% 的比例混合在一起。
>
> ---
>
> ### 3. 工程与效果上的优缺点对比
>
> | 对比维度         | **Query2Doc（文本拼接后生成）**                              | **HyDE（向量空间数学融合）**                                 |
> | :--------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **融合层级**     | 语义/词汇层级的非线性融合                                    | 几何/空间层级的线性插值                                      |
> | **权重的可控性** | **不可控**。<br>原问题短、伪文档长，拼在一起时长文本往往会“反客为主”，把短问题的注意力稀释淹没。 | **完全自由可控**。<br>可以用数学公式精准调整比例：<br>$V = \alpha V_{原问题} + (1-\alpha) V_{伪文档}$<br>比如让原问题占 20%，伪文档占 80%，或者像你刚才那样把原问题设为 0%（`include_query=False`）。 |
> | **独立性**       | 原问题和扩写文本强绑定在一起。                               | 两者解耦。你可以只用伪文档，也可以缓存原问题向量，灵活性极高。 |
>
> ### 总结
> * **“生成一个混合向量”** 是在**输入端（文字端）**做加法，交给神经网络去消化；
> * **“在向量空间中融合”** 是在**输出端（坐标端）**做数学加法，由你用数学公式完全掌控两个语义所占的权重比例。

> ⭐⭐**“查询改写”是什么检索增强技术？**
>
> 
>
> 在检索增强生成（RAG）系统中，**“查询改写”（Query Rewriting）**属于 **检索前阶段（Pre-Retrieval）** 的核心优化技术，通常也被统称为 **查询转换（Query Transformation）**。
>
> ---
>
> ### 一、 核心定义与定位
>
> * **所属阶段**：**Pre-Retrieval（检索前增强）**
> * **核心目的**：在用户问题进入检索器（向量检索 / BM25 稀疏检索 / 混合检索）之前，利用大模型（LLM）等能力，将用户的原始问题**重新组织、规范化或扩充**，生成一个或多个**更利于知识库检索**的 Query。
>
> ---
>
> ### 二、 解决的核心痛点
>
> 在真实的 RAG 系统中，用户直接输入的问题往往不适合直接检索，查询改写主要解决以下 3 个问题：
>
> 1. **词汇/语义鸿沟（Vocabulary Mismatch & Semantic Gap）**：
>    * 用户习惯用**生活化、口语化**语言表达（如：“*临时外出需要怎么申请*”）；
>    * 知识库/制度文档通常用**书面化、规范化、专业术语**书写（如：“*考勤管理办法*”、“*因公外出审批流程*”、“*打卡报备规程*”）。
>    * 如果直接做 BM25 或向量检索，命中精度和召回率通常较低。
> 2. **意图模糊与信息缺失**：
>    * 用户问题常包含客套话（“*我想了解下...*”）、模糊代词（“*那个怎么弄*”），改写可以过滤噪音、提炼核心意图。
> 3. **缺少领域上下文**：
>    * 将通用问题置于特定业务场景（如你的代码中指定的“*公司员工规章制度*”）下，补充领域专有名词。
>
> ---
>
> ### 三、 结合你代码的分析
>
> 在你的代码中：
> ```python
> prompt_template = """你是一名公司员工制度的问答助手, 熟悉公司规章制度。
> 你的任务是需要为给定的问题，从不同层次生成这个问题的转述版本，使其更易于检索，转速的版本增加一些公司规章制度的关键词
> 问题: {question}
> 转速版本:"""
> ```
> 这是一种典型的 **Prompt-based 领域关键词注入型改写（Domain-Specific Query Paraphrasing）**：
> * **输入**：`我想了解下,临时外出需要怎么申请`（口语化、含无意义前缀词）
> * **改写后的预期输出**：类似 `员工临时因公/因私外出考勤管理规章制度及审批流程申请说明`
> * **检索提升点**：去除了客套词“我想了解下”，补充了制度维度的关键词（“考勤”、“审批”、“规章制度”），使向量空间和关键词倒排索引与知识库文档的契合度大幅提升。
>
> ---
>
> ### 四、 RAG 中常见的查询改写/转换模式
>
> 除了代码中的**单句关键词增强**，在进阶 RAG 体系中，查询改写技术还包含以下几种常见形态：
>
> | 技术名称                                    | 工作原理                                                     | 适用场景                                                     |
> | :------------------------------------------ | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **多查询扩展 (Multi-Query)**                | 让 LLM 从不同角度生成 3~5 个等价或互补的 Query 分别检索，最后去重合并 | 提高**召回率（Recall）**，避免单次检索由于措辞偏差遗漏关键内容 |
> | **RAG-Fusion**                              | 在 Multi-Query 的基础上，对多个检索结果列表使用倒数排名融合（RRF）加权排序 | 兼顾**召回率**与**排序相关性**                               |
> | **假设性文档嵌入 (HyDE)**                   | 先让 LLM 根据提问生成一篇“虚构但格式符合的假答案”，再拿假答案的向量去检索真实知识库 | 适合**文档很长、提问很短**，直接提问无法匹配语义的场景       |
> | **子问题分解 (Sub-Question Decomposition)** | 将复杂问题拆解为多个步骤/子问题（如：“*对比 A 和 B 部门的外出流程*” $\rightarrow$ “*A 部门外出流程*” + “*B 部门外出流程*”） | 复杂多跳（Multi-Hop）查询                                    |
> | **回退提问 (Step-Back Prompting)**          | 从具体问题提炼出一个更高级别、更抽象的概念问题先检索背景知识 | 涉及底层原理、规章框架层面的问题检索                         |
>
> ---
>
> ### 五、 实践建议（小贴士）
>
> 1. **修正 Prompt 中的错别字**：代码 Prompt 中的 `转速版本` 建议修改为 `转述版本`，避免干扰小参数模型的理解。
> 2. **控制 LLM 改写的幻觉**：Prompt 中可以增加约束 `“保持原意，不要预设答案，仅提取并补全检索关键词”`，防止大模型在改写时过度推演。

#### Take step back

#### 定义

> **Take a Step Back**（通常称为 **Step-Back Prompting** 或 **“退后一步”抽象检索技术**）最早由 Google DeepMind 在 2023 年的论文 *《Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models》* 中提出。
>
> 在 RAG（检索增强生成）系统中，它是一种非常关键的**查询转换与重写（Query Transformation / Rewriting）**技术。
>
> ---
>
> ### 一、核心思想与直觉
>
> 在实际检索中，用户的原始提问往往**过于具体、细节繁杂、或包含过多约束条件**。如果直接拿着具体问题去向量数据库或搜索引擎中检索，常常会遇到以下问题：
> - 检索到的文档碎片化，充斥着无关细节；
> - 知识库中可能没有一模一样的具体案例，但实际上包含了底层的**通用原理、基础概念或背景知识**。
>
> **“Take a Step Back” 的思想是：**
> > 面临一个复杂的具体问题时，先让模型**“退后一步”**，思考这个问题背后更宽泛、更高层次的**核心概念、基本原理或背景事实**是什么，并基于抽象问题进行检索，最后将原理知识与具体问题结合推导出答案。
>
> ---
>
> ### 二、工作流程与原理
>
> 典型的 Step-Back RAG 包含以下三个核心步骤：
>
> ```
>                     ┌───────────────────┐
>                     │  用户原始具体问题   │
>                     └─────────┬─────────┘
>                               │
>                     ┌─────────▼─────────┐
>                     │ LLM: 退后一步提问  │
>                     │ (Step-Back Query) │
>                     └─────────┬─────────┘
>                               │
>              ┌────────────────┴────────────────┐
>              ▼                                 ▼
>    【检索具体问题事实】               【检索抽象原理/背景】
>     Retrieve(Original)                 Retrieve(Step-Back)
>              │                                 │
>              └────────────────┬────────────────┘
>                               │ 知识拼接与融合
>                               ▼
>                     ┌───────────────────┐
>                     │  LLM 综合推理并解答 │
>                     └───────────────────┘
> ```
>
> 1. **抽象提问（Step-Back Question Generation）**：
>    * 引导 LLM 对原问题进行降维/升华抽象，剥离特异性细节。
>    * **示例 1（物理/常识）：**
>      * **原问题**：如果将密封容器中理想气体的温度从 $20^\circ\text{C}$ 升到 $80^\circ\text{C}$，压强会如何变化？
>      * **Step-Back 问题**：理想气体状态方程中，温度和压强遵循什么物理定律？
>    * **示例 2（学术/历史）：**
>      * **原问题**：Estella Leopold 在 1950 年到 1960 年期间曾就读于哪个学校？
>      * **Step-Back 问题**：Estella Leopold 的教育经历和学术背景是怎样的？
> 2. **双路检索（Dual Retrieval）**：
>    * 针对**原始问题**检索具体的实体、数字或细节事实。
>    * 针对 **Step-Back 抽象问题**检索高阶原理、定律或全局背景。
> 3. **融合生成（Answer Generation with Principles）**：
>    * 将高阶原理知识和具体事实 context 一同输入给大模型。大模型在底层原理指导下进行推理，得出原问题的准确结论。
>
> ---
>
> ### 三、Prompt 实现示例
>
> 通常在 LLM 的 Prompt 中加入少量示例（Few-Shot），让它学会如何“退后一步”：
>
> ```text
> 你是一个善于提炼高层次概念的专家。请针对用户提出的复杂具体问题，退后一步，提出一个更高阶、更抽象的问题，该问题应涵盖解答原问题所需的基础概念、原则或背景知识。
> 
> 示例 1:
> 原问题: 某款电动汽车在冬天-10°C环境下续航下降了35%，可能是什么原因？
> Step-Back 问题: 低温环境对锂离子电池放电性能和容量衰减的影响机制是什么？
> 
> 示例 2:
> 原问题: 乔布斯在离开苹果创立 NeXT 期间，哪家公司投资了他？
> Step-Back 问题: NeXT 公司的创立历史与早期投资背景是怎样的？
> 
> 请为以下问题生成 Step-Back 问题：
> 原问题: {input_query}
> Step-Back 问题:
> ```
>
> ---
>
> ### 四、与其他检索增强技术的对比
>
> | 技术方案                                 | 核心方向                                       | 适用场景                                                 |
> | :--------------------------------------- | :--------------------------------------------- | :------------------------------------------------------- |
> | **Step-Back**                            | **纵向向上抽象**（求通识、物理法则、高层背景） | 复杂多跳推理、需要专业原理/理论支撑的问题                |
> | **Sub-Query Decomposition** (子问题拆分) | **横向分解步骤**（分而治之，先算A再算B）       | 复合问题（例如：“A公司和B公司2023年谁的营收增速更快？”） |
> | **HyDE** (假设性文档嵌入)                | **生成伪答案**（直接预测一段答案文本再做匹配） | 问句短、语义稀疏、问答匹配度较低的场景                   |
> | **Multi-Query** (多查询改写)             | **同级水平扩展**（同义改写、多角度提问）       | 避免用户单次提问用词偏门导致的漏召回                     |
>
> ---
>
> ### 五、总结
>
> **Take a Step Back** 技术的核心价值在于**“以原理指导细节”**。它通过大模型的抽象能力将复杂的具体查询转化为高维概念，极大地弥补了传统向量检索在**多跳逻辑推导、常识常理运用和宏观背景召回**方面的不足，显著降低了 RAG 系统的幻觉率。

from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, FewShotChatMessagePromptTemplate

def take_step_back(query):
    examples = [
        {
            "input": "我祖父去世了，我要回去几天",
            "output": "公司丧葬假有什么规定？",
        },
        {
            "input": "我去北京出差，北京的消费高，有什么额外的补助",
            "output": "员工出差的交通费、住宿费、伙食补助费的规定是什么",
        },
    ]
    example_prompt = ChatPromptTemplate.from_messages(
        [
            ("human", "{input}"),
            ("ai", "{output}"),
        ]
    )
    few_shot_prompt = FewShotChatMessagePromptTemplate(
        example_prompt=example_prompt,
        examples=examples,
    )
    prompt = ChatPromptTemplate.from_messages(
        [
            (
                "system",
                """你是一名公司员工制度的问答助手, 熟悉公司规章制度。你的任务是将输入的问题通过归纳、提炼，转换为关于公司规章制定相关的一般性的问题，使得这些问题更容易捕捉问题的意图。请参考下面的例子：""",
            ),
            # Few shot examples
            few_shot_prompt,
            # New question
            ("user", "{question}"),
        ]
    )
    question_gen = prompt | langchain_llm | StrOutputParser()
    res = question_gen.invoke({"question": query})
    return res.split("<|endoftext|>")[0]

##### 多索引检索--父子检索

> ⭐️⭐️**你给我解释下“多索引检索-父子检索”下的代码是什么意思？**
>
> 
>
> 这部分代码实现的是 RAG 检索进阶中非常经典的**父子检索（Parent-Child Retrieval / Small-to-Big Retrieval）**策略。
>
> ---
>
> ### 一、为什么需要“父子检索”？（核心思想）
>
> 在常规 RAG 中，文档切分面临一个**矛盾**：
> - **切片太大（父文档）**：上下文完整，适合大模型阅读理解；但内容混杂，向量化后语义容易被稀释，检索时经常匹配不准。
> - **切片太小（子文档）**：语义聚焦明确，检索召回率极高；但如果直接把这几十个字扔给大模型，由于严重缺乏上下文，大模型很容易断章取义或回答不准。
>
> **父子检索的解决思路是：“小块检索，大块回答”**：
> 1. 把大块文档（父文档）进一步切成极细碎的小块（子文档）。
> 2. **只对小块做向量化并存入向量库**，小块中附带父文档的 `doc_id`。
> 3. **大块文档原样保存在一个 KV 存储（Docstore）中**。
> 4. 检索时，用用户的 Query 去匹配小块，命中后通过 `doc_id` 反查并返回对应的**完整大块文档**给大模型。
>
> ---
>
> ### 二、逐段代码详细解释
>
> #### 1. 定义子切片文本分割器
> ```python
> from langchain_core.documents import Document
> from langchain_text_splitters import RecursiveCharacterTextSplitter
> 
> # 用于切分更小文本块的切分器
> child_text_splitter = RecursiveCharacterTextSplitter(
>     chunk_size=64,     # 极其紧凑的切片长度，仅64个字符
>     chunk_overlap=15,  # 重叠15个字符，保持边界连贯
>     separators=[       # 按段落、换行、各种中英文标点符号依次切分
>         "\n\n", "\n", ".", "．", "。", ",", "，", "、"
>     ]
> )
> ```
> - **作用**：构建一个专门切小文本块的切分器，将句子切得很细（约一两句话），让每个小块的语义高度纯粹，便于向量召回。
>
> ---
>
> #### 2. 生成子文档并关联父文档 ID
> ```python
> sub_docs = []
> id_key = "doc_id"
> index_type = 'sm_chunk'
> 
> for i, doc in enumerate(docs):
>     _id = doc_ids[i]
>     # 如果是表格，不要切小块，保持整表结构
>     if doc.metadata["is_table"] == 1:
>         _doc = Document(page_content=doc.page_content,
>                         metadata={"type": index_type, id_key: _id})
>         sub_docs.extend([_doc])
>         continue
>     
>     # 普通文本切分成多个子文档
>     _sub_docs = child_text_splitter.split_documents([doc])
>     
>     # 关键步骤：每个子文档都绑定对应父文档的 id (_id)
>     for _doc in _sub_docs:
>         _doc.metadata[id_key] = _id
>         _doc.metadata["type"] = index_type
>     
>     sub_docs.extend(_sub_docs)
> ```
> - **核心逻辑**：
>   - `docs` 是原始的较大文档（父文档），每个父文档都有对应的唯一 ID `doc_ids[i]`。
>   - **特殊处理表格**：表格一旦按字符切碎就会丢失行/列对应关系，因此表格保持完整，不切小块。
>   - **绑定血缘关系**：普通文本切成细小的 `_sub_docs` 后，把父文档的 `_id` 存入子文档的 `metadata['doc_id']` 中。
>
> ---
>
> #### 3. 将子文档向量化存入向量库
> ```python
> # 1. 清理旧 collection
> try:
>     chroma_client.delete_collection("zhidu_db_sm_chunk")
> except Exception:
>     pass
> 
> # 2. 初始化 Chroma 向量库集合
> sm_chunk_db = Chroma(
>     collection_name="zhidu_db_sm_chunk",
>     embedding_function=embedding,
>     client=chroma_client,
> )
> 
> # 3. 分批写入向量库（每批16条）
> batch_size = 16
> for i in range(0, len(sub_docs), batch_size):
>     batch = sub_docs[i : i + batch_size]
>     sm_chunk_db.add_documents(batch)
>     print(f"写入进度: {min(i + batch_size, len(sub_docs))}/{len(sub_docs)}")
> ```
> - **作用**：
>   - 向量库中存且仅存**子文档**的 embedding 向量和文本内容。
>   - 分批（batch=16）是为了避开 Embedding 模型 API（如阿里云百炼/DashScope 单次最多 16~20 条文本）的请求限制。
>
> ---
>
> #### 4. 构建 `MultiVectorRetriever` 串联父子关系
> ```python
> from langchain.storage import InMemoryByteStore
> from langchain.retrievers.multi_vector import MultiVectorRetriever
> 
> # 1. 创建存放父文档的内存存储（基于键值对的 ByteStore）
> store = InMemoryByteStore()
> id_key = "doc_id"
> 
> # 2. 初始化多向量检索器
> retriever = MultiVectorRetriever(
>     vectorstore=sm_chunk_db,  # 负责做向量检索的子库
>     byte_store=store,         # 负责存放完整大文档的父库
>     id_key=id_key,            # 两者用来关联的键名
> )
> 
> # 3. 将所有原始父文档（大块）存入 store，以 doc_id 为键
> retriever.docstore.mset(list(zip(doc_ids, docs)))
> ```
> - **两个存储各司其职**：
>   1. `sm_chunk_db`（向量库）：只存小块向量，用于算余弦相似度。
>   2. `store`（KV 存储）：存放完整的父文档原始内容。
> - `MultiVectorRetriever` 封装了检索自动转换的整个流程。
>
> ---
>
> #### 5. 检索与验证
> ```python
> query = "出差交通费怎么算？"
> retriever.invoke(query)
> ```
> - **执行过程**：
>   1. `sm_chunk_db` 检索 Query，匹配出最接近的几个子小块（比如仅有几十个字的一句规章条文）。
>   2. 从匹配到的子块中读取 `metadata['doc_id']`。
>   3. 自动到 `store` 中按 `doc_id` 查出**原本完整的整篇规章或段落（包含表格、上下文等完整内容）**，返回给外部。
>
> 作为对比，后面的代码：
> ```python
> sm_chunk_db.similarity_search(query, k=2)
> ```
> 直接搜向量库，返回的仅仅是孤立的 64 字符碎块（例如：`。出差人员的市内交通费按出差的自然（日历）天数计算，每人每天80 元包干使用`）；而 `retriever.invoke()` 返回的是包含整个差旅标准规章、表格与上下文的完整文档。
>

> 要理解**“向量化后语义容易被稀释，检索时经常匹配不准”**，我们可以从**生活比喻、技术底层原理、具体业务案例**三个层面来拆解：
>
> ---
>
> ### 1. 直观比喻：颜料调色
>
> * **小切片（子文档）**：就像**一滴纯正的红色颜料**（只讲一件具体的事，比如“出差打车怎么报销”）。
> * **大切片（父文档）**：就像**一大桶水**，里面不仅滴了红色，还混了黄色的“考勤打卡”、蓝色的“请假审批”、黑色的“违纪处罚”……最后搅拌成了一桶**“灰褐色”**。
>
> 当用户的 Query 是“出差打车怎么报销”（用户拿出了**鲜红色**）：
> * 拿着鲜红色去和那一滴纯红对比，匹配度几乎是 99%；
> * 拿着鲜红色去和那桶混合后的灰褐色对比，颜色被严重稀释，匹配度可能只剩 40%，系统就会觉得“它俩不太相关”，从而在检索中把它漏掉。
>
> ---
>
> ### 2. 技术底层原理：固定维度的信息压缩
>
> Embedding 模型（向量化）的核心逻辑是：**把任意长度的文本，压缩成一个固定长度的数值向量（例如常见的 768 维或 1536 维）**。
>
> 1. **容量固定与信息挤压**：
>    - 无论是一句话（20字）还是一大篇长文（2000字），输出的都是一个 1536 维的向量。
>    - 文本越长，向量的每个维度就必须去分担编码更多不同的概念。
> 2. **平均池化（Pooling）抹平了细节**：
>    - Transformer 模型在生成整个切片的向量时，通常会通过注意力加权或均值池化把所有词的特征融合起来。
>    - 如果一个切片里讨论了 5 个不同的话题，这个向量在高维空间中代表的就是这 5 个话题的**“折中方向/中心重心”**，而不是其中任何一个具体话题的特征。
> 3. **余弦相似度计算失真**：
>    - 向量检索比的是向量的方向夹角（余弦相似度）。
>    - 用户的 Query 往往非常简短、聚焦（单一语义方向）；而长文本的向量方向被其他无关段落“拉偏了”，导致计算出的相似度得分大幅下降。
>
> ---
>
> ### 3. 具体业务案例：为什么明明有答案却搜不到？
>
> 假设公司制度里有一篇 1500 字的大文档《员工考勤与出差综合规范》：
> * 前 1200 字都在讲：**打卡考勤、迟到扣款、事假病假、违纪开除流程**；
> * 只有最后 50 字顺带写了一句：*“员工出差产生的市内交通费，按实际出差自然天数计算，每人每天 80 元包干使用。”*
>
> 此时：
> * **用户提问**：“出差交通补贴一天多少钱？”
> * **向量化结果**：
>   - 这篇大文档被转化为向量时，**80% 以上的信息权重都被“考勤打卡、违规处罚”霸占了**，整篇文档的语义重心偏向于“劳动纪律”。
>   - 模型算出来的文档向量，在高维空间里离“劳动纪律”很近，而离用户的“交通补贴”非常远。
> * **检索后果**：
>   - 系统根据相似度排序，排在前几名的可能是别的短文档，而这篇真正包含答案的大文档因为相似度得分太低，**直接被排在 Top-K 之外，导致召回失败（检索漏掉）**。
>
> 这就是所谓的**“语义被稀释，检索匹配不准”**。
>
> ---
>
> ### 总结：父子检索为什么能破局？
>
> * **切成子文档（小块）**：那句 *“出差产生的市内交通费，每人每天 80 元包干使用”* 被独立成一个 60 字的子向量。此时它就是**纯红色**，和用户的 Query 在空间中方向完全一致，能够以超高相似度被瞬间击中。
> * **找回父文档（大块）**：击中后再通过 `doc_id` 把 1500 字的整篇制度取出来丢给大模型。大模型拿到的是包含前后文、逻辑完整的材料，既不会漏查，也不会断章取义。

> 在 `## 多索引检索-总结检索` 这一章节中，核心实现的是 LangChain 的 **多向量检索技术（MultiVectorRetriever）** 中的 **“文档摘要检索（Summary Retrieval）”** 策略。
>
> ---
>
> ### 一、 核心设计思想与解决的痛点
>
> 在传统的 RAG 检索中，通常是**“用什么内容建向量索引，检索时就召回什么内容”**。这会带来分块粒度的两难权衡：
> * **分块太长**：Embedding 向量会被长文本中的杂乱信息稀释，导致语义匹配度下降（容易搜不准）。
> * **分块太短**：虽然向量匹配准了，但召回给大模型的上下文片段过于残缺，LLM 容易因缺少上下文而产生幻觉。
>
> **“多索引-总结检索”的核心思路是：【检索（索引）与投喂（存储）分离】**
> 1. **用于检索匹配的库（Chroma 向量库）**：只存由大模型提炼的**“简短摘要与关键词”**，语义集中、特征鲜明，更容易与用户的提问匹配；
> 2. **用于给 LLM 答题的真实存储（ByteStore 存储库）**：存完整的**“原始文档块”**，确保上下文充足；
> 3. **两者的桥梁**：通过全局唯一的 `doc_id` 进行关联。
>
> ---
>
> ### 二、 各段代码逐行解析
>
> #### 1. 导入依赖与初始化大模型
> ```python
> from langchain_core.documents import Document
> from langchain_core.output_parsers import StrOutputParser
> from langchain_core.prompts import ChatPromptTemplate
> from model import QwenLLM
> 
> llm = QwenLLM()
> ```
> * 导入构建 LangChain 处理链所需的 `Document`（文档结构体）、`StrOutputParser`（输出文本解析器）和 `ChatPromptTemplate`（提示词模板）。
> * 初始化通义千问模型 `QwenLLM()`，后续用它来给各个文档分块生成摘要。
>
> ---
>
> #### 2. 定义 Prompt 模板与生成摘要的 Chain
> ```python
> prompt_template = "你是企业员工助手，熟悉公司考勤和报销标准等规章制度。请根据下面的文档:\n\n{doc}\n 做一个简短的概括摘要改写，字数50字，并给出关键词"

> * **LCEL 处理链**：
>   1. `{"doc": lambda x: x.page_content}`：从传入的 `Document` 中提取纯文本内容；
>   2. 填入提示词模板；
>   3. 送入大模型；
>   4. 通过 `StrOutputParser()` 转为字符串输出。

> ```python

> ```
> * 对前面章节切分好的原始文档集合 `docs` 进行批处理，生成每篇文档的摘要列表 `summaries`。
> * `max_concurrency=1`：设置并发量为 1（单并发顺序执行），防止瞬时并发过高触发 API 限流。

>     doc = docs[i]

>         continue
>

>                  metadata={"type": index_type, id_key: _id})
>     
>     summary_docs.extend([_s])
> ```

> * **关键关联点**：在 metadata 中注入了 `{id_key: _id}`（即 `doc_id`），保证这个摘要能对应回它所属的原始完整文档。
>

> ```python

>                                      embedding_model.get_embedding_fun(),
>                                      client=chroma_client,
>                                      collection_name="zhidu_db_summary",
>                                      )
> ```
> * 将 `summary_docs`（包含摘要和表格原内容）灌入专门的集合 `zhidu_db_summary` 中计算向量并建索引。
>
> ---
>
> #### 6. 组装 MultiVectorRetriever
> ```python
> store = InMemoryByteStore()
> id_key = "doc_id"
> 
> # The retriever (empty to start)
> summary_retriever = MultiVectorRetriever(
>     vectorstore=summary_chunk_db,
>     byte_store=store,
>     id_key=id_key,
> )
> summary_retriever.docstore.mset(list(zip(doc_ids, docs)))
> ```
> * `InMemoryByteStore()`：内存键值数据库（Docstore），专门用来存真实文档。
> * `MultiVectorRetriever` 核心三要素：
>   1. `vectorstore=summary_chunk_db`：负责向量匹配的库（里面存的是精简摘要）。
>   2. `byte_store=store`：负责存取实际完整文档的文档库。
>   3. `id_key="doc_id"`：两者之间的外键字段。
> * `docstore.mset(...)`：把 `(doc_id, docs)` 以键值对形式存入 `store`。
>
> ---
>
> #### 7. 检索测试与对比验证
> ```python
> query = "出差交通费怎么算？"
> summary_retriever.invoke(query)
> ```
> * **调用效果**：
>   1. 用户的 query 进入 `summary_retriever`；
>   2. 检索器在 `zhidu_db_summary`（摘要向量库）中计算相似度，命中相关摘要；
>   3. 根据命中摘要的 `doc_id`，自动去 `InMemoryByteStore` 查找出**原始完整文档**；
>   4. 返回给上层的是完整的长文档（包含制度全文及表格细节），避免了信息丢失。
>
> ```python
> summary_chunk_db.similarity_search(query, k=2)
> ```
> * 这一行是对底层的向量库直接做单点查询，目的是向读者演示：**向量库里实际命中的确实是带有关键词的 50 字简短摘要**（例如 `“摘要：市内交通费为出差期间每日80元定额...”`），证明了检索命中走的是摘要，但对外交付的是全文。
>

>
> ```

>          │                                   │
>    存入 DocStore                       存入 向量库 (Chroma)
>   (ByteStore, key=doc_id)             (包含 doc_id 字段)
> 
> 2. 在线检索阶段：
>    用户 Query ──> 向量匹配检索摘要 ──> 获取命中 doc_id ──> 从 DocStore 取出完整原始文档并返回
> ```

> ### 一、核心设计思想：为什么要用“假设问题检索”？
>
> 在常规 RAG 中，用户输入的是**疑问句/提问**（如 *“出差交通费怎么算？”*），而数据库里存的是**陈述句/制度正文**（如 *“市内交通费按自然天数计算，每人每天80元……”*）。  
> 提问和陈述句在语义空间中常常存在“表述鸿沟（Query-Document Mismatch）”。
>
> **假设问题检索的解决思路：**
> 1. **预处理阶段**：让大模型（LLM）阅读每个文档切片，提前猜测并生成若干个**“可能被问到的问题”**。
> 2. **多向量索引（Multi-Vector）**：
>    - **向量库（Vector Store）**：只存这些**“假设问题”**及其向量（每个问题绑定原始文档的 `doc_id`）。
>    - **文档库（Doc Store）**：存完整的**“原始文档块”**。
> 3. **检索阶段（Query-to-Query）**：用户提问时，系统在向量库中寻找最相似的“假设问题”（疑问句对疑问句，语义匹配度显著提升）；命中后，再通过 `doc_id` 自动把**原始文档**返回给 LLM 生成答案。

##### 三种多索引检索的区别



> 这三种检索方式都属于 LangChain 中基于 **`MultiVectorRetriever`** 的**多索引/多向量检索**架构。
>
> 它们的核心思想完全相同：**“检索阶段（搜索代理向量）”与“生成阶段（返回上下文）”解耦**——无论在向量库中搜到了什么，最终通过 `doc_id` 返回给大模型的都是**内容完整、上下文连贯的原始文档（Parent Document）**。
>
> 三者的**根本区别在于：用什么样的“代理内容（Key）”在向量库中建立索引**，以解决不同的检索痛点：
>
> ---
>
> ### 一、对比维度速览
>
> 按照你的对比维度，将 **“父子检索”**、**“总结检索”** 与 **“假设问题检索”** 完整梳理对比如下：
>
> | 维度               | 父子检索（Parent-Child / Small-to-Big）                      | 总结检索（Summary Retrieval）                                | 假设问题检索（Hypothetical Questions Retrieval）             |
> | :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **索引库里存什么** | 切得很小的原文子文本块（如 64 字符的小切片）                 | 由大模型提炼的浓缩摘要 + 关键词（如 50 字）                  | 由大模型预先生成的**若干个假设性问句**（如每段生成 3 个疑问句） |
> | **存储库里存什么** | 完整的父文档（未二次切分的大块）                             | 完整的原始文档                                               | 完整的原始文档                                               |
> | **索引项生成方式** | **机械切分**（通过 `RecursiveCharacterTextSplitter` 规则切分） | **语义生成**（调用 LLM 批量理解并概括改写）                  | **语义生成**（调用 LLM 预测用户可能提出的疑问，并结构化解析） |
> | **映射关系**       | **1 对 多**（1 个父文档对应多个子切片）                      | **1 对 1**（1 个原始文档对应 1 个摘要）                      | **1 对 多**（1 个原始文档对应 3 个假设问题）                 |
> | **建库开销与耗时** | **极低**：纯本地字符串切分，耗时毫秒级，无 Token 成本        | **较高**：每个文档块都要调用 LLM 生成摘要，耗时且消耗 Token  | **最高**：每个文档块都要调用 LLM 生成多个问句，需要重试和格式校验，耗时最长且向量库索引数量成倍膨胀（如 3 倍） |
> | **语义特征**       | 局部的、具体的字面原文（陈述句细节）                         | 高维抽象的、浓缩的、富含关键词的概括（陈述句核心）           | **疑问句形态、用户意图导向、契合口语/搜索提问风格的问题表述** |
> | **匹配模式**       | **细节 $\leftrightarrow$ 细节**（Query 找匹配的原文字句/参数） | **主题 $\leftrightarrow$ 主题**（Query 找匹配的主题和关键词） | **问题 $\leftrightarrow$ 问题**（**Query-to-Question**，疑问句直接对齐疑问句） |
> | **核心解决痛点**   | 长文本块语义稀释、细节特征被平均化导致漏搜                   | 冗余修饰与背景噪音多、长段落主题分散                         | **提问（疑问句）与文档（陈述句）之间的表达鸿沟与语法错位**   |
> | **最适合的场景**   | 精确数值、细碎条例、技术规范中查找某句话或参数               | 宏观政策说明、背景报告、长篇材料的核心主题概括检索           | **智能客服、企业制度咨询（HR/财务报销等 FAQ 问答型场景）**   |
>
> ---
>
> ### 二、深入解析三者逻辑与代码差异
>
> #### 1. 父子检索（Parent-Child Retrieval）
> * **原理**：把大文档（Parent）切成很多超小块（Child，如 64 字符）。向量库只索引小块。
> * **为什么有效**：大分块（如 1000 字符）往往包含多个语义主题，经过 Embedding 向量化后，局部细节（如某个报销比例、某个时间点）的特征会被稀释。切成小块后，每一块语义高度单一、纯粹，更容易被精准命中；命中后，系统自动拿回完整的大分块，保证回答时上下文不丢失。
> * **典型场景**：技术参数查询、法律规章里的特定罚则/数值条款。
>
> #### 2. 总结检索（Summary Retrieval）
> * **原理**：用 LLM 将文档块浓缩成 50 字的摘要和核心关键词，向量库只索引这段摘要。
> * **为什么有效**：很多规章制度包含大段的套话、背景说明、修饰语。这些非核心词汇在 Embedding 时会成为“噪声”。摘要去除了冗余细节，提炼了**高密度的核心意图和主题词**，能够更精准地响应概括性、方向性的查询。
> * **典型场景**：“差旅费包括哪些开支？”、“介绍一下考勤的基本规定”这类偏宏观主题的提问。
>
> #### 3. 假设问题检索（Hypothetical Questions Retrieval）
> * **原理**：让 LLM 预先针对该分块内容设想 3 个“可以从中找到答案的问题”，向量库索引这 3 个问题。
> * **为什么有效**：这是典型的 **Query-to-Query** 模式。自然语言中，“如何请假？”和“员工因公晚到应事先履行请假手续”在句式、用词和语法上有很大差异，Embedding 距离可能偏远；但如果把文档转化成“教职员工因故晚到需要履行什么手续？”，用户的问题与索引里的问题就是“问句对问句”，语义相似度极高。
> * **典型场景**：智能客服、员工制度问答（FAQ 场景），用户的提问意图非常明确直接。
>
> ---
>
> ### 三、工程选型与实践建议
>
> 1. **资源有限 / 吞吐量大**：
>    - 优先选择 **父子检索**。无需消耗大模型 API 额度生成索引，切分快、成本低，却能有效兼顾“检索精度”与“生成上下文完整性”。
> 2. **制度条款 / 知识问答类场景**：
>    - **假设问题检索** 的召回表现通常优于普通向量检索，因为企业内部员工几乎都是以“疑问句”提问，与预生成的假设问题语义最接近。
> 3. **混合多索引（进阶做法）**：
>    - 实际生产中，三者并不互斥。可以将同一篇原始文档的“小分块向量”、“摘要向量”、“假设问题向量”打上不同 metadata，放入同一个多向量索引库中。只要命中任意一种形式的代理向量，都能关联捞出完整的父文档。

>     weights=[0.3, 0.7]

>   LangChain 的 `EnsembleRetriever` 默认使用 **RRF（Reciprocal Rank Fusion）** 算法。它不仅看各检索器给出的绝对分数，更关注文档在每个检索器中的**排位（Rank）**：
>   $$\text{RRF Score}(d) = \sum_{r} w_r \times \frac{1}{k + \text{rank}_r(d)}$$
>   其中：
>   - `weights=[0.3, 0.7]`：赋予 BM25 检索器 0.3 的权重，向量语义检索器 0.7 的权重。
>   - 根据两个检索器的排名及权重综合计算出加权总得分，重新排序后输出。

> ⭐️⭐️**所以BM25检索和向量语义检索各自是怎么样去检索的？**
>
> 
>
> 我们可以把这两种检索机制分别看作：**“按图索骥的查字典法”（BM25）** 与 **“心领神会的高维几何测距法”（向量语义检索）**。
>
> 下面为您详细拆解它们各自底层的检索过程和原理：
>
> ---
>
> ### 一、BM25 检索（基于字面与统计的稀疏检索）
>
> BM25（Best Matching 25）是传统搜索引擎（如 ElasticSearch、Lucene）的核心算法，它是经典的 **TF-IDF 的升级改良版**。
>
> #### 1. 检索过程
> 1. **分词与倒排索引（提前建好）：**
>    - 知识库中的文档被切分成词（例如通过 `jieba` 分词）。
>    - 建立“**词 $\rightarrow$ 出现该词的文档列表**”的倒排索引表（Inverted Index）。
> 2. **查询分词与召回候选：**
>    - 用户输入 Query，例如 `“我要请病假”`，分词为 `["我", "要", "请", "病假"]`。
>    - 拿这些词去倒排索引表中快速查出包含这些词的所有候选文档。
> 3. **计算 BM25 相关性得分：**
>    对每个命中的词计算分值，然后累加：
>    $$\text{Score}(Q, D) = \sum_{q \in Q} \text{IDF}(q) \times \frac{\text{TF}(q, D) \times (k_1 + 1)}{\text{TF}(q, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$
>    公式看起来复杂，但本质只看**三个维度**：
>    - **词的稀缺性（IDF）：** 一个词在整个语料库里越少见，权重越高。比如“的、要”几乎每篇都有，权重极低；而“病假”很少见，权重极高。
>    - **词频非线性饱和（TF）：** 某个词在当前文档出现次数越多越相关。但 BM25 做了一个**平滑上限**（$k_1$ 参数调控），出现 1 次到 2 次提升明显，但出现 10 次和 100 次得分相差无几，防止恶意堆砌关键词。
>    - **文档长度惩罚（Length Normalization）：** 篇幅特别长的文档词频往往自然偏高，BM25 会根据平均文档长度（$\text{avgdl}$）进行归一化惩罚，偏向更精炼的段落。
> 4. **排序输出：** 将总分从高到低排序，返回前 $k$ 个片段。
>
> ---
>
> ### 二、向量语义检索（基于概念与向量空间的稠密检索）
>
> 向量检索（Dense Retrieval）依赖**深度学习神经网络（Embedding 模型）**。它不依赖字面是否完全一致，而是把文本的“意思”转化成数字。
>
> #### 1. 检索过程
> 1. **离线向量化（建库阶段）：**
>    - 知识库中的每个文档片段送入 Embedding 模型（如 BERT、BGE、OpenAI text-embedding 等）。
>    - 模型将一段文字压缩成一个固定维度的多维向量（例如 768 维或 1536 维的浮点数数组，如 `[0.12, -0.04, 0.85, ...]`）。
>    - 这个向量就相当于该文本在“语义世界”中的**空间坐标**，存入向量数据库（如 Chroma）。
> 2. **在线查询向量化（Query Embedding）：**
>    - 用户提问 `“休婚假的流程”`，用**同一个 Embedding 模型**将其也转换成一个 768 维的查询向量。
> 3. **计算几何相似度（空间距离计算）：**
>    - 在高维向量空间中，计算查询向量与各个文档向量之间的**夹角余弦（Cosine Similarity）**或内积：
>      $$\text{Cosine Similarity} = \cos(\theta) = \frac{\vec{A} \cdot \vec{B}}{\|\vec{A}\| \|\vec{B}\|}$$
>    - 夹角越小（余弦值越接近 1），说明两个向量在高维空间中越近，代表**语义越相似**。
>    - （工业界通常借助 HNSW、IVF 等向量索引技术加速计算，避免全量逐一对比）。
> 4. **排序输出：** 按相似度从大到小，返回距离最近的前 $k$ 个片段。
>
> ---
>
> ### 三、直观对比：为什么它们需要“融合”？
>
> 我们可以通过两个典型场景看出两者的互补性：
>
> | 场景                | 用户查询                     | 文档库原文                                            | BM25 的检索表现                                              | 向量语义检索的表现                                           |
> | :------------------ | :--------------------------- | :---------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **同义/概念改写**   | *“怎么开具离职证明？”*       | *“员工解除劳动合同流转审批表办理规范”*                | ❌ **失效（分数为0）**<br>因为“离职证明”这几个字根本没在原文里出现过。 | ✅ **精准命中**<br>模型理解“解除劳动合同”和“离职”在高维语义空间极其接近。 |
> | **专有名词/长编号** | *“查一下型号 RTX-4090D-24G”* | *“RTX-4090-24G 使用手册”* 与 *“RTX-4090D-24G 说明书”* | ✅ **精准命中**<br>字面必须严格包含特定后缀“4090D”，不会搞混。 | ❌ **容易混淆**<br>模型可能认为这两个型号都是显卡，语义向量过于相似，可能召回错误型号。 |
>
> ### 总结
>
> - **BM25 怎么查**：分词 $\rightarrow$ 查倒排索引字典 $\rightarrow$ 算词频与稀缺性统计分 $\rightarrow$ 精确字面匹配。
> - **向量语义怎么查**：编码为高维向量 $\rightarrow$ 计算空间夹角（余弦相似度） $\rightarrow$ 模糊语义匹配。
> - **融合检索（Ensemble）**：利用 RRF 算法将两者的排名加权整合，同时获得了 **BM25 的“准”（不漏专有名词）** 和 **向量检索的“懂”（理解近义表述）**。



> **那他们是怎么融合在一起的？比如说现在是weights=[0.3, 0.7]，那么是分别用BM25检索还有向量语义检索出结果后再合在一起吗？**
>
> **是的，完全正确！**
>
> 融合检索的执行逻辑正是：**“先分别独立检索，再通过融合算法合并重新排队”**。
>
> 但是，这里有一个大家初学时最容易产生的误解：
> > **误区**：“融合是不是直接用公式 `0.3 × BM25分数 + 0.7 × 向量相似度分数`？”  
> > **答案**：**绝对不行！**
>
> ### 为什么不能直接加权原始分数？
>
> 因为两者的**分数体系完全不同，根本没有可比性（量纲不同）**：
> - **向量相似度（余弦相似度）**：取值通常在 `[0, 1]` 之间，比如 `0.85`、`0.72`。
> - **BM25 检索得分**：根据词频和文档库大小动态计算，通常是无上限的正实数，比如 `15.6`、`38.2`、甚至几百。
>
> 如果直接拿 `0.3 × 38.2 + 0.7 × 0.85`，BM25 的几十倍数值会彻底淹没向量分数，设置的 `[0.3, 0.7]` 权重就形同虚设了。
>
> ---
>
> ### 真正的融合过程：RRF（加权互惠排名融合）
>
> 在 LangChain 的 `EnsembleRetriever` 中，默认采用学术和工业界最成熟的 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 算法。
>
> 它的核心思想是：**“不管你原始分是多少，我只看你在各自榜单里的名次（Rank）”**。
>
> #### 计算公式：
> $$\text{总分}(d) = \sum_{i} \text{权重}_i \times \frac{1}{c + \text{名次}_i(d)}$$
> *(其中 $c$ 是平滑常数，LangChain 默认设为 60，避免第 1 名的分数高得太离谱)*。
>
> ---
>
> ### 举个具体例子带你走一遍全流程：
>
> 假设用户提问：`“公司丧假有什么规定？”`，设置 `weights=[0.3, 0.7]`。
>
> #### 第一步：分别独立检索
> 两个检索器各自去搜，返回各自的前 3 名：
> - **BM25 榜单**（关键词命中）：
>   - 第 1 名：**文档 A**
>   - 第 2 名：**文档 B**
>   - 第 3 名：**文档 C**
> - **向量语义检索 榜单**（语义理解）：
>   - 第 1 名：**文档 B**
>   - 第 2 名：**文档 D**
>   - 第 3 名：**文档 A**
>
> ---
>
> #### 第二步：根据名次和权重算综合分
>
> - **对于【文档 B】**（两边都看好它）：
>   - BM25 排第 2 名：$0.3 \times \frac{1}{60 + 2} \approx 0.0048$
>   - 向量检索排第 1 名：$0.7 \times \frac{1}{60 + 1} \approx 0.0115$
>   - **综合得分** = $0.0048 + 0.0115 = \mathbf{0.0163}$ 🏆
>
> - **对于【文档 A】**（BM25第一，向量第三）：
>   - BM25 排第 1 名：$0.3 \times \frac{1}{60 + 1} \approx 0.0049$
>   - 向量检索排第 3 名：$0.7 \times \frac{1}{60 + 3} \approx 0.0111$
>   - **综合得分** = $0.0049 + 0.0111 = \mathbf{0.0160}$
>
> - **对于【文档 D】**（仅向量检索排第 2）：
>   - BM25 没排进前列：$0$
>   - 向量检索排第 2 名：$0.7 \times \frac{1}{60 + 2} \approx \mathbf{0.0113}$
>
> - **对于【文档 C】**（仅 BM25 排第 3）：
>   - BM25 排第 3 名：$0.3 \times \frac{1}{60 + 3} \approx \mathbf{0.0048}$
>   - 向量检索没排进前列：$0$
>
> ---
>
> #### 第三步：重新合并排序输出
> 按综合分重新从高到低排队：
> 1. **文档 B**（0.0163）
> 2. **文档 A**（0.0160）
> 3. **文档 D**（0.0113）
> 4. 文档 C（0.0048）
>
> 取前 3 名（`k=3`），最终返回的就是 **[文档 B, 文档 A, 文档 D]**。
>
> ---
>
> ### 这套融合机制的核心收益：
> 1. **自动对齐量纲**：通过转化为“名次倒数”，自然消除了不同算法数值范围不同的问题。
> 2. **权重真正生效**：因为向量权重是 `0.7`（BM25 是 `0.3`），在同样拿第 1 名的情况下，向量检索推崇的文档会拿到明显更高的基础分。
> 3. **“共识优先”**：**两方都认为相关**的文档（如上面的文档 B），会获得双重加分，自然被推到最前列。

>

>
> ```python

>

>
> ---
>
> ### 2. 在线查询阶段（每次提问时）：直接查内存里的倒排索引
>
> 当用户提出问题时：
> ```python
> query = "我要请病假100天"
> ret_docs = bm25_retriever.invoke(query)
> ```
> 此时已经**不再访问向量库了**，而是直接在刚刚建好的内存倒排索引表里按词检索、计算 BM25 分数、快速返回匹配最高的切片。
>
> ---
>
> ### 深入补充：为什么要先全部“捞”出来？
>
> 为什么不能像向量检索那样，直接向 Chroma 发起一条带 BM25 的查询，而非得把全部文档先拉到 Python 内存里？
>
> 1. **算力与算法原理限制**：  
>    BM25 要算某个词的重要性（IDF），**必须事先知道“整个库一共有多少文档”、“这个词在全库中一共出现了多少次”**。如果不把全部切片过一遍，就根本算不出全局词频。
> 2. **轻量级向量库的功能局限**：  
>    早期的 Chroma 主要专精于向量相似度计算，本身没有内置像 Lucene 那样的全文倒排索引引擎。LangChain 提供的 `BM25Retriever` 是一个**纯 Python 内存级的轻量实现**（基于 `rank_bm25` 库），所以必须把所有文档一口气喂给它。
>
> ---
>
> ### 扩展：在生产环境中也是这么做吗？
>
> - **在小规模项目 / 教程学习时（当前代码）**：
>   文档切片数量较小（几千到小几万条），全量拉到内存建倒排索引非常快（几秒钟搞定），而且纯本地运行，方便易用。
> - **在企业级海量数据场景（几十万到几千万切片）**：
>   把所有切片拉到 Python 内存会导致**内存爆炸、服务启动极其缓慢**。此时通常会采用以下架构：
>   - **原生混合检索向量库**（如 **Elasticsearch / OpenSearch、Milvus 2.4+、Qdrant、Weaviate**）：在切片入库时，数据库底层就会**同时**建好向量索引（HNSW）和倒排索引（BM25），检索时直接由数据库内部完成各自检索与融合，不需要把全部切片拉到应用内存中。

### 三、 逐段代码拆解分析

#### 1. 灵活的分支检索（多策略兼容设计）
```python
if context_query_type == "vector":
    related_docs = zhidu_db.similarity_search_by_vector(context_query, k=k)
elif context_query_type == "query":
    related_docs = zhidu_db.similarity_search(context_query, k=k)
elif context_query_type == "doc":
    related_docs = context_query
else:
    related_docs = zhidu_db.similarity_search(context_query, k=k)
```
这里是该函数最精妙的设计点：
- **`"query"`（普通文本检索）**：传入的是文本（如原始问题、改写后的问题、或者拼接了伪文档的 Query2Doc），Chroma 会自动将其先`转换为 Embedding`，再去计算向量相似度。
- **`"vector"`（向量直接检索）**：传入的直接是一个 Embedding 向量。常用于 **HyDE（假设文档嵌入）** 技术——先让大模型生成一篇虚构答案，并提前提取出向量，直接送入向量库做相似度计算。
- **`"doc"`（绕过检索）**：直接传入预处理好的文档列表。常用于 **Rerank（重排序）** 或多路召回融合后，文档已经挑选好了，直接送进流水线组装回答即可。

#### 2. 上下文组装与打印调试
```python
context = "\n".join([f"上下文{i+1}: {doc.page_content} \n" 
                     for i, doc in enumerate(related_docs)])
print(f"query: {query}")
print(f"context: {context}")
```
- 将召回的多个文档切片（`Document`）的文本内容提取出来，加上序号（`上下文1:`、`上下文2:`）格式化拼接。
- 显式打印 `query` 和 `context`，方便开发者直观看到：**到底检索到了哪些内容、有没有召回有效制度，还是检索到了无关噪音**。

#### 3. 提示词（Prompt）格式化
```python
prompt = PromptTemplate(
            input_variables=["question", "context"],
            template=prompt_template)
llm_prompt = prompt.format(question=query, context=context)
```
- 利用 LangChain 的 `PromptTemplate`，将真实的原始问题 `query` 和刚才检索到的 `context` 注入模板，构成送给大模型的完整指令。

#### 4. 大模型生成（支持流式）
```python
if stream:
    response = llm(llm_prompt, stream=True)
    print(f"response: ")
    for chunk in response:
        content = chunk.choices[0].delta.content or ""
        print(content, end='', flush=True)
    return ""
else:
    response = llm(llm_prompt, stream=False, temperature=temperature)
    return response
```
- **流式（Stream=True）**：调用 LLM 接口逐 chunk 读取大模型生成的内容，使用 `flush=True` 在控制台实现打字机效果，大幅降低用户的首字等待感知。
- **非流式（Stream=False）**：等待模型完全生成后，将完整字符串返回给外部调用方（通常用于自动化评估、批量评测等场景）。

### 四、 总结：为什么要将 `query` 和 `context_query` 分开？

这个函数之所以将 **`query`（提问）** 和 **`context_query`（检索词）** 拆成两个入参，核心是为了支持 **Query-Driven 的高级 RAG 优化算法**：
1. **普通 RAG**：`run_rag_pipline(query, query)`（提问什么就去搜什么）；
2. **Query2Doc**：`run_rag_pipline(query, query2doc(query))`（用扩展后的伪文档去搜真实文档，但最终仍回答用户的原始问题）；
3. **HyDE**：`run_rag_pipline(query, doc_embedding, context_query_type="vector")`（用假设文档的向量去搜，但最终仍回答原始问题）。
