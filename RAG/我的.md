## 2.html

### WebBaseLoader

~~~python
from langchain_community.document_loaders import WebBaseLoader

loader = WebBaseLoader("https://flask.palletsprojects.com/en/3.0.x/tutorial/layout/"
docs = loader.load()

for doc in docs:
    print(doc.page_content, doc.metadata)
~~~

> ⭐**解析**
>
> * **`loader = WebBaseLoader(...)`**
>   * 创建一个网页加载器，告诉它要读取哪个网页。此时只是准备好加载器。
> * **`docs = loader.load()`**
>   * 实际访问网页、提取文字，并将结果保存到 `docs`。它返回的是 **`Document` 对象组成的列表**，不是普通字符串。
> * 在 RAG 中，这属于**加载数据**这一步。之后通常还要进行文本切分、向量化和检索；这两行本身没有调用大模型。
>
> ⭐⭐**page_content打印的内容是什么？**
>
> * `page_content` 是从网页 HTML 中提取出的文字，不是经过整理的文章正文。
>
> * 可以把这个过程理解为：
>
>   ~~~
>   网页 HTML → 去掉 HTML 标签、提取文字 → page_content
>   ~~~
>
>

### BeautifulSoup

~~~python
from bs4 import BeautifulSoup

html_txt = ''
with open('./data/test.html', 'r') as f:
    for line in f.readlines():
        html_txt += line
        
soup = BeautifulSoup(html_txt, 'lxml')
code_content = soup.find_all('div', class_='highlight')

for ele in code_content:
    print(ele.text)
    print("+"*100)
~~~



> ⭐**你的代码可以分成四步理解。**
>
> **1. 读取本地 HTML**
>
> ```python
> html_txt = ''
> with open('./data/test.html', 'r') as f:
>     for line in f.readlines():
>         html_txt += line
> ```
>
> 逐行读取文件，再拼接成一个字符串。结合前面的编码问题，这里可以简化成：
>
> ```python
> with open('./data/test.html', 'r', encoding='utf-8') as f:
>     html_txt = f.read()
> ```
>
> **2. 解析 HTML**
>
> ```python
> soup = BeautifulSoup(html_txt, 'lxml')
> ```
>
> 让 BeautifulSoup 使用 `lxml` 解析器，把 HTML 解析成可以按标签查找的结构。
>
> **3. 筛选代码块**
>
> ```python
> code_content = soup.find_all('div', class_='highlight')
> ```
>
> 查找所有类似这样的元素：
>
> ```python
> <div class="highlight">
>     <pre>from flask import Flask</pre>
> </div>
> ```
>
> 这里并不是自动识别“哪些内容是代码”，而是**根据 HTML 的标签和 class 筛选**。在这个网页中，代码块使用了 `highlight` 类，所以能这样提取。
>
> **4. 打印每个代码块**
>
> ```python
> for ele in code_content:
>     print(ele.text)
>     print("+" * 100)
> ```
>
> `ele.text` 获取该元素内的文字；`"+" * 100` 打印 100 个加号，用来分隔不同代码块。
>
> 它们之间还有一个关系：**`BSHTMLLoader` 本身也使用 BeautifulSoup 来解析 HTML**，只是帮你封装了读取、提取文字和创建 `Document` 的步骤。你现在直接使用 BeautifulSoup，就能自行控制只提取哪些部分。

### 三者区别

这段代码是在**手动读取本地 HTML，并只提取其中的代码块**；前面的两个加载器`默认提取网页中的整体文字`，并`包装成 LangChain 文档`。

| 对比项       | 这段 BeautifulSoup 代码 | `BSHTMLLoader`   | `WebBaseLoader`  |
| ------------ | ----------------------- | ---------------- | ---------------- |
| 来源         | 本地 HTML 文件          | 本地 HTML 文件   | 在线网页         |
| 提取范围     | 指定的代码块            | 默认提取整体文字 | 默认提取整体文字 |
| 结果形式     | 当前代码直接打印字符串  | `Document` 列表  | `Document` 列表  |
| 来源等元数据 | 需要自己添加            | 加载器添加       | 加载器添加       |





## 3.pdf

### PyMuPDFLoader

~~~python
from langchain_community.document_loaders import PyMuPDFLoader

loader = PyMuPDFLoader('./data/zhidu_travel.pdf')
docs = loader.load()

for doc in docs:
    print(doc)
    print("="*100)
~~~

> ⭐⭐**这个是pdf里的文字都会提取出来吗，然后print(doc)默认就是打印doc.page_content吗？最后是按什么标准生成docs列表的？**
>
> 
>
> 可以分成三个问题理解。
>
> **1. PDF 里的文字都会提取出来吗？**
>
> 它会逐页提取 PDF 中**可以解析的文本**，但不保证提取到所有视觉上可见的文字：
>
> - 普通文字型 PDF：通常能直接提取文字。
> - 扫描件、图片里的文字：你这段代码默认没有开启 OCR，可能提取不到。
> - 复杂表格、多栏排版：可能提取出文字，但顺序和格式不一定与原页面一致。
>
> **2. `print(doc)` 等于 `print(doc.page_content)` 吗？**
>
> **不等于。** `print(doc)` 会调用文档对象的字符串表示，通常同时包含 `page_content` 和 `metadata`。[Document 源码](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/documents/base.py)
>
> ```
> print(doc)               # 文本内容和元数据
> print(doc.page_content)  # 只打印文本内容
> print(doc.metadata)      # 只打印元数据，比如来源文件、页码
> ```
>
> 例如，`print(doc)` 的输出大致是：
>
> ```
> page_content='这是第一页的文字……' metadata={'source': './data/zhidu_travel.pdf', 'page': 0, ...}
> ```
>
> 而 `print(doc.page_content)` 只会输出：
>
> ```
> 这是第一页的文字……
> ```
>
> **3. `docs` 列表是按照什么标准生成的？**
>
> 你这种默认用法是**按照 PDF 的页来生成，每页对应一个 `Document`**，不是按段落、标题或固定字数切分。[PyMuPDFLoader 文档](https://reference.langchain.com/python/langchain-community/document_loaders/pdf/PyMuPDFLoader)
>
> 你截图里 `docs` 有 3 个元素，按默认分页方式，对应：
>
> ```
> docs
> ├── docs[0] → 第 1 页的 Document
> ├── docs[1] → 第 2 页的 Document
> └── docs[2] → 第 3 页的 Document
> ```
>
> 可以这样查看：
>
> ```
> for doc in docs:
>     print(f"第 {doc.metadata['page'] + 1} 页")  # page 从 0 开始
>     print(doc.page_content)
>     print("=" * 100)
> ```
>
> 注意：**`Document` 本身不一定代表一页**。这里一页一个对象，是 `PyMuPDFLoader` 的加载方式决定的；之后使用文本切分器，还可以把一页再拆成多个 `Document`。





### fitz

~~~python
import fitz

doc = fitz.open('./data/zhidu_travel.pdf')

table_data = []
text_data = []


doc_tables = {}
for idx, page in enumerate(doc):
    text = page.get_text()
    text_data.append(text)
    tabs = page.find_tables()
    for i,tab in enumerate(tabs):
        ds = tab.to_pandas()
        table_data.append(ds.to_markdown())
        
for tab in table_data:
    print(tab)
    print("="*100)
~~~

> ⭐**这代码具体做了什么？**
>
> ```python
> for idx, page in enumerate(doc):
> ```
>
> 逐页遍历 PDF，`idx` 是从 0 开始的页序号，`page` 是当前页面。
>
> ```python
> text = page.get_text()
> text_data.append(text)
> ```
>
> 提取当前页的文字，保存到 `text_data`。因此通常有：
>
> ```python
> text_data[0]  # 第 1 页文字
> text_data[1]  # 第 2 页文字
> ```
>
> 接下来单独处理表格：
>
> ```python
> tabs = page.find_tables()     # 检测当前页的表格
> 
> for i, tab in enumerate(tabs):
>     ds = tab.to_pandas()      # 表格转为 pandas DataFrame
>     table_data.append(ds.to_markdown())  # 再转为 Markdown 字符串
> ```
>
> 例如，保存的字符串可能是：
>
> ```python
> |    | 交通方式 | 报销标准 |
> |---:|:---------|:---------|
> |  0 | 火车     | 二等座   |
> |  1 | 飞机     | 经济舱   |
> ```
>
> **两个列表的划分标准不同：**
>
> ```python
> text_data  → 每页一个字符串
> table_data → 每个检测到的表格一个字符串
> docs       → 默认每页一个 Document
> ```
>
> 假设 PDF 有 3 页，第 1 页有 2 张表，第 2 页没有表，第 3 页有 1 张表，那么：
>
> ```python
> len(text_data)  # 3，对应 3 页
> len(table_data) # 3，对应 3 张表
> len(docs)      # 3，对应 3 页
> ```
>
> 虽然长度碰巧相同，代表的内容并不一样。而且你的 `table_data` 没有保存页码，无法直接看出每张表来自哪一页。
>
> 
>
> **还有两点需要注意：**
>
> - `page.get_text()` **可能已经包含表格里的文字**，所以 `text_data` 和 `table_data` 可能存在内容重复。
> - 第一段最后只遍历了 `table_data`，因此**正文虽然提取了，却没有打印出来**。`doc_tables = {}` 则没有在后续代码中使用。
>
> 如果你需要把表格保留成行列结构，第一段提供了明确的处理流程；⭐`如果是把 PDF 按页加载到 LangChain 中进行后续切分和检索，使用PyMuPDFLoader更方便。`

### 两者区别

主要区别是：**第一段直接使用 PyMuPDF，分别提取文字和表格；第二段使用 LangChain 封装的加载器，默认按页提取文字并生成 `Document` 列表。**

`fitz` 就是 PyMuPDF 的导入名称，所以两段代码底层使用的是同一个 PDF 处理库。

| 对比项       | 第一段：`fitz`                    | 第二段：`PyMuPDFLoader`              |
| ------------ | --------------------------------- | ------------------------------------ |
| 操作方式     | 自己逐页处理 PDF                  | 加载器封装处理过程                   |
| 普通文字     | 存在 `text_data` 中，每项是字符串 | 存在 `docs` 中，每项是 `Document`    |
| 表格         | 显式识别，转换为 Markdown 表格    | 当前代码未配置结构化表格提取         |
| 页码、来源   | 需要自己保存                      | 自动放在 `metadata` 中               |
| 最后打印什么 | 只打印提取到的表格                | 打印每页的文档对象，包含文字和元数据 |



> ⭐**import fitz和from langchain\_community.document\_loaders import PyMuPDFLoader是用的同一个底层库吗？**
>
> 
>
> 是的，**两者底层都使用 PyMuPDF**，只是调用层次不同：
>
> ```
> 你的代码 → fitz（PyMuPDF）→ PDF
> 你的代码 → PyMuPDFLoader → PyMuPDF → PDF
> ```
>
> - **`import fitz`**：直接使用 PyMuPDF，你自己控制逐页读取、文字提取、表格识别等操作。
> - **`PyMuPDFLoader`**：LangChain 对 PyMuPDF 的封装，帮你处理加载流程，并把结果整理成包含 `page_content` 和 `metadata` 的 `Document` 对象。
>
> 因此，**底层库相同，但输出形式和默认处理流程不同**。`fitz` 是 PyMuPDF 历史沿用的导入名称。

### Unstructured

**`unstructured`是一个Python库，主要用于处理`非结构化数据，如文本、PDF文档、电子邮件`等。这个库可以帮助你从这些非结构化的数据源中提取信息**

- pip install -i https://pypi.tuna.tsinghua.edu.cn/simple langchain_unstructured
- unstructured文档： https://docs.unstructured.io/open-source/core-functionality/partitioning





~~~python
from langchain_unstructured import UnstructuredLoader

loader = UnstructuredLoader('./data/zhidu_travel.pdf')
docs = loader.load()

for doc in docs:
    print(doc)
    print("="*100)
~~~



### UnstructuredLoader和PyMuPDFLoader的区别

最大的区别是：**你这两段代码中，`UnstructuredLoader` 默认按识别出的“文档元素”生成 `Document`，`PyMuPDFLoader` 默认按“页”生成 `Document`。**

两者返回的都是 `Document` 列表，所以后面的 `for doc in docs` 写法一样，但每个 `doc` 代表的内容不同。

| 对比项          | `UnstructuredLoader`           | `PyMuPDFLoader`  |
| --------------- | ------------------------------ | ---------------- |
| 使用的解析工具  | Unstructured                   | PyMuPDF          |
| 默认拆分单位    | 标题、正文段落、列表项等元素   | PDF 的每一页     |
| 一个 `Document` | 通常对应一个识别出的元素       | 对应一页文字     |
| 元数据          | 可能包含元素类别、页码、坐标等 | 包含来源、页码等 |
| 支持的文件范围  | PDF、Word、HTML 等多种格式     | 主要用于 PDF     |

这些默认行为可参见 [UnstructuredLoader 文档](https://reference.langchain.com/python/langchain-unstructured/document_loaders/UnstructuredLoader) 和 [PyMuPDFLoader 文档](https://reference.langchain.com/python/langchain-community/document_loaders/pdf/PyMuPDFLoader)。

**举个例子：同一页 PDF 包含这些内容**

```
差旅管理制度              ← 标题

员工出差需提前提交申请。   ← 正文段落

一、交通费用              ← 小标题

高铁按二等座标准报销。     ← 正文段落
```

用 `PyMuPDFLoader`，默认会得到 **1 个 Document**：

```
Document(
    page_content="差旅管理制度\n员工出差需提前提交申请。\n一、交通费用\n高铁按二等座标准报销。",
    metadata={"page": 0, ...}
)
```

用 `UnstructuredLoader`，**可能得到多个 Document**，例如：

```
Document(page_content="差旅管理制度",
         metadata={"category": "Title", ...})

Document(page_content="员工出差需提前提交申请。",
         metadata={"category": "NarrativeText", ...})

Document(page_content="一、交通费用",
         metadata={"category": "Title", ...})

Document(page_content="高铁按二等座标准报销。",
         metadata={"category": "NarrativeText", ...})
```

这是示意，具体数量和分类取决于页面内容、解析策略及识别结果，并不保证每个自然段都恰好对应一个元素。

你可以这样查看 Unstructured 实际拆出了什么：

```
for doc in docs:
    print("类别：", doc.metadata.get("category"))
    print("页码：", doc.metadata.get("page_number"))
    print("内容：", doc.page_content)
    print("=" * 100)
```

**因此，同一个 3 页 PDF，用 `PyMuPDFLoader` 默认得到 3 个文档；用 `UnstructuredLoader` 可能得到几十个文档。** 这不一定意味着提取的文字更多，往往只是拆分得更细。另外，使用 Unstructured 并不意味着表格、扫描文字一定能正确识别，效果还取决于解析配置。



> ⭐**我感觉UnstructuredLoader是逐行提取文字的**
>
> 
>
> **更准确的结论是：`PyMuPDFLoader` 默认按页拆分；`UnstructuredLoader` 按解析器识别出的元素拆分，这些元素可能是标题、段落，也可能只是单行文字。** 我这里还没有运行你环境中的 Unstructured，不能仅凭源 PDF 确定它实际拆出了哪些元素。

#### MSO_SHAPE_TYPE

~~~python
from pptx import Presentation
from pptx.enum.shapes import MSO_SHAPE_TYPE
ppt = Presentation('./data/test_ppt.pptx')

for slide_number, slide in enumerate(ppt.slides, start=1):
    print(f"Slide {slide_number}:")
    for shape in slide.shapes:
        if shape.has_text_frame:
            print(shape.text)
            
        if shape.has_table:
            table = shape.table 
            for row_idx, row in enumerate(table.rows):  
                for col_idx, cell in enumerate(row.cells): 
                    cell_text = cell.text  
                    print(f"Row {row_idx + 1}, Column {col_idx + 1}: {cell_text}")  
            
        if shape.shape_type == MSO_SHAPE_TYPE.PICTURE:
                    image = shape.image
                    image_filename = './data/test.jpg'
                    with open(image_filename, 'wb') as f:
                        f.write(image.blob)
~~~





#### 两者区别



核心区别是：**第一种把 PPT 内容整理成适合 LangChain 使用的文档；第二种直接访问 PPT 的页面、文本框、表格和图片，由你决定怎么处理。**

它们并不完全是两套独立的解析技术：Unstructured 的 `.pptx` 解析内部也使用了 `python-pptx`，再增加内容分类和整理逻辑。[Unstructured 源码](https://github.com/Unstructured-IO/unstructured/blob/main/unstructured/partition/pptx.py)

| 对比项           | `UnstructuredPowerPointLoader`             | `python-pptx`                        |
| ---------------- | ------------------------------------------ | ------------------------------------ |
| 抽象层级         | 较高：加载并整理文档内容                   | 较低：直接操作 PPT 对象              |
| 你这段代码的结果 | 返回 `list[Document]`                      | 打印文本、表格，并把图片写入文件     |
| 文本             | 自动提取，支持区分标题、正文等元素         | 用 `shape.text` 读取，分类规则自己写 |
| 表格             | 可提取为表格元素，保留结构取决于模式和参数 | 直接访问行、列、单元格               |
| 图片             | 你这段调用没有实现图片导出或图片内容识别   | `image.blob` 可以导出原始图片        |
| 页码等信息       | 取决于加载模式和元素元数据                 | 在逐页遍历时自行记录                 |
| 自定义程度       | 适合快速接入文档处理流程                   | 适合精细控制提取过程                 |

**1. 第一段的 `docs`，默认不是“一页一个 Document”**

你的代码：

```python
loader = UnstructuredPowerPointLoader("./data/test_ppt.pptx")
docs = loader.load()
```

默认使用 `mode="single"`，将提取出的内容合并成一个 `Document`。因此，即使 PPT 有很多页，通常也只得到一个文档对象。

其中：

```python
doc.page_content  # 提取出的文本
doc.metadata      # 来源等元数据
```

如果希望区分标题、段落、表格等元素，可以使用：

```python
loader = UnstructuredPowerPointLoader(
    "./data/test_ppt.pptx",
    mode="elements",
)

docs = loader.load()

for doc in docs:
    print(doc.page_content)
    print(doc.metadata)
```

此时**一个元素对应一个 Document，也不等于一页一个 Document**。元素元数据可以包含类别、页码等信息。[LangChain 文档](https://reference.langchain.com/python/langchain-community/document_loaders/powerpoint/UnstructuredPowerPointLoader)

**2. 第二段是在自己编写提取规则**

你明确规定了三类处理：

```python
if shape.has_text_frame:
    # 读取文本框文字

if shape.has_table:
    # 按行、列读取单元格文字

if shape.shape_type == MSO_SHAPE_TYPE.PICTURE:
    # 导出图片文件
```

这种方式可以更方便地保留“第几页、哪个表格、第几行、第几列”等信息。但你目前只是 `print()`，**并没有把内容收集成供后续检索使用的文档列表**。

另外，当前循环只检查页面顶层的形状。若文本、图片位于组合形状中，需要递归遍历组合内部的 `shape.shapes`。[python-pptx 形状文档](https://python-pptx.readthedocs.io/en/stable/api/shapes.html)

**3. 你保存图片的代码有两个需要注意的地方**

```python
image_filename = "./data/test.jpg"
```

- 每张图片都使用相同文件名，后面的图片会覆盖前面的图片。
- `image.blob` 是原始图片数据；把扩展名写成 `.jpg`，不会把 PNG 等格式转换为 JPEG。

可以给图片使用独立文件名，并保留真实扩展名：

```python
# 配合：for shape_idx, shape in enumerate(slide.shapes, start=1):
image = shape.image
image_filename = (
    f"./data/slide_{slide_number}_image_{shape_idx}.{image.ext}"
)

with open(image_filename, "wb") as f:
    f.write(image.blob)
```

`blob` 和 `ext` 分别提供图片的二进制数据与相应扩展名。[python-pptx 文档](https://python-pptx.readthedocs.io/en/latest/api/image.html)

**导出图片不等于识别图片内容。** 第二段不会自动读取截图中的文字，也不会理解图片中的流程图；这需要额外接入 OCR 或视觉模型。

⭐`对于你的 RAG 学习场景：`

- **快速实现 PPT 文本检索**：第一种更省代码，可以接着做文本切分、向量化和检索。
- **需要保留页面、单元格位置，或单独处理图片**：第二种更灵活，再把提取结果封装成 LangChain 的 `Document`。
- **需要理解截图、图表、流程图**：在内容提取之外，增加图片识别或视觉理解步骤。

### 代码

~~~python
import numpy as np
from langchain_community.document_loaders import PyMuPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_experimental.text_splitter import SemanticChunker

doc_path = './data/zhidu_travel.pdf'
loader = PyMuPDFLoader(doc_path)
docs = loader.load()
data = []
for doc in docs:
    data += doc.page_content.split('。')

word_nums = [len(txt) for txt in data if len(txt) != 0]
np.mean(word_nums)
np.min(word_nums)
np.max(word_nums)
np.percentile(word_nums, q=95)
~~~

> **代码解析**
>
> 
>
> 这段代码是在**读取 PDF，按中文句号拆分文本，再统计每段文本的字符数分布**，可以用来了解文档长度，为后续分块大小提供参考。
>
> 逐步来看：
>
> ```
> loader = PyMuPDFLoader('./data/zhidu_travel.pdf')
> docs = loader.load()
> ```
>
> 读取 PDF。在这个用法中，`docs` 通常是按页组织的文档列表，`doc.page_content` 是对应页的文本。
>
> ```
> data = []
> for doc in docs:
>     data += doc.page_content.split('。')
> ```
>
> 把每页文本按中文句号 `。` 拆开，再汇总到 `data`。例如：
>
> ```
> "住宿费凭据报销。交通费每天80元。".split('。')
> # ['住宿费凭据报销', '交通费每天80元', '']
> ```
>
> 这里只按句号拆分，并没有真正理解句子；跨页的句子也不会自动拼接。
>
> ```
> word_nums = [len(txt) for txt in data if len(txt) != 0]
> ```
>
> 计算每个非空片段的长度。**这里统计的是字符数，不是词数，也不是 token 数**；空格、换行、数字和标点也计入长度。
>
> 接下来四项统计：
>
> | 代码                             | 含义                   |
> | -------------------------------- | ---------------------- |
> | `np.mean(word_nums)`             | 平均字符数             |
> | `np.min(word_nums)`              | 最短片段的字符数       |
> | `np.max(word_nums)`              | 最长片段的字符数       |
> | `np.percentile(word_nums, q=95)` | 字符数的第 95 百分位数 |
>
> 例如，第 95 百分位数是 `200`，可以理解为：**大约 95% 的片段长度不超过 200 个字符**。百分位数可能通过插值计算，因此结果不一定是整数。
>
> 
>
> **有两个细节：**
>
> - `RecursiveCharacterTextSplitter` 和 `SemanticChunker` 只是导入了，这段代码没有使用它们。
> - 在 notebook 同一个单元格中，通常只自动显示最后一个表达式的结果。想看到全部统计值，可以写：
>
> ```
> print("平均字符数：", np.mean(word_nums))
> print("最少字符数：", np.min(word_nums))
> print("最多字符数：", np.max(word_nums))
> print("95%分位字符数：", np.percentile(word_nums, q=95))
> ```



> **np.percentile(word\_nums, q=95) 是什么意思？**
>
> 
>
> `np.percentile(word_nums, q=95)` 是计算 `word_nums` 的**第 95 百分位数**。
>
> 在你的代码中，`word_nums` 保存了各个文本片段的字符数。假设：
>
> ```
> np.percentile(word_nums, q=95)
> # 200.0
> ```
>
> 可以理解为：
>
> > 大约 95% 的文本片段不超过 200 个字符，剩下约 5% 更长。

### 和上述PyMuPDFLoader的区别

## 8.递归文本分块：RecursiveCharacterTextSplitter

### 代码

~~~python
from langchain_community.document_loaders import PyMuPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

doc_path = './data/zhidu_travel.pdf'
loader = PyMuPDFLoader(doc_path)

r_spliter = RecursiveCharacterTextSplitter(
    chunk_size=128,
    chunk_overlap=30,
    separators=[
        "\n\n",
        "\n",
        ".",
        "．",  # 全角句点
        "。",  # 中文句号
        ",",
        "，",  # 中文逗号
        "、",  # 顿号
    ],
)

split_docs = loader.load_and_split(r_spliter)

print(split_docs[0].page_content)
print(split_docs[1].page_content)

docs = loader.load()
split_docs = r_spliter.split_documents(docs)
print(split_docs[0].page_content)
~~~



> ⭐**代码解析**
>
> 
>
> 这段代码的作用是：**先定义文本切分规则，再读取文档，并按照规则把文档切成小块**，方便后续做 RAG 检索。
>
> **1. `r_spliter` 是一个文本切分器**
>
> ```
> r_spliter = RecursiveCharacterTextSplitter(
>     chunk_size=128,
>     chunk_overlap=30,
>     separators=[...],
> )
> ```
>
> 各参数的含义：
>
> | 参数               | 含义                                                         |
> | ------------------ | ------------------------------------------------------------ |
> | `chunk_size=128`   | 每块的目标最大长度为 128 个字符，默认按 `len()` 计数，不是 token 数 |
> | `chunk_overlap=30` | 相邻块之间目标重叠 30 个字符，帮助保留上下文；实际不一定恰好重叠 30 个 |
> | `separators=[...]` | 按优先级尝试的切分位置                                       |
>
> “递归切分”可以理解为：先尝试按 `"\n\n"`（段落）切，某段仍太长，就继续尝试 `"\n"`（换行），再尝试句号、逗号等。短片段还会被合并成合适大小的块，并非每遇到一个标点都单独生成一块。[官方切分说明](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)
>
> **2. `loader.load_and_split(r_spliter)` 是“加载 + 切分”**
>
> `loader` 是你前面创建的**文档加载器对象**，具体读取 PDF、文本文件还是网页，要看它的类型。
>
> ```
> split_docs = loader.load_and_split(r_spliter)
> ```
>
> 在 LangChain 标准加载器中，基本等价于：
>
> ```
> # 第一步：读取数据，得到 Document 列表
> docs = loader.load()
> 
> # 第二步：使用你定义的切分器，切成更小的 Document
> split_docs = r_spliter.split_documents(docs)
> ```
>
> 这里传入的 `r_spliter` 就是在告诉加载器：**“加载完成后，用这个切分器处理文档。”**
>
> 返回的 `split_docs` 是 `Document` 对象列表，不只是字符串。可以这样查看：
>
> ```

> print(split_docs[0].page_content)   # 第一块的文本
> print(split_docs[0].metadata)       # 来源、页码等信息，具体取决于加载器
> ```
>
> 当前官方文档已将 `load_and_split` 标注为应视为`弃用`，因此新代码更建议使用上面的两步写法，过程也更清楚。[加载器 API 文档](https://reference.langchain.com/python/langchain-core/document_loaders/base/BaseLoader)
>
> **3. 你的分隔符列表可以补一个 `""`**
>
> ```

> ```
>
> 末尾的空字符串表示：如果文本太长，而且没有可用的分隔符，最后就按字符切分。你原来的列表没有这个兜底，所以某些块可能超过 128 个字符。

>

# 检索增强技术

### 第一部分：文件中实现的检索增强技术全景详解

#### 一、 Query（查询端）增强技术

用户原始提问往往存在**太短、口语化、含糊或场景具象**的问题，代码中实现了 5 种不同的查询变换策略：

##### 1. Query2Doc（基于大模型生成伪文档增强检索）

- **核心原理**：在检索前，先让 LLM 凭借自身已有的参数知识，针对用户问题先生成一段简短回答（称为“伪文档” Pseudo-Document）；然后将 `用户原问题 + 伪文档` 拼接在一起，组成一段更长、词汇更丰富的文本，再去向量数据库检索。
- **解决痛点**：用户原始问题只有几个字，语义信息太稀疏，难以在向量空间中准确匹配几百字的长文档。
- **代码实现**：定义了 `def query2doc(query)`，利用大模型生成初步回答 `doc_info`，构造 `context_query = f"{query}, {doc_info}"` 后送入检索器。

##### 2. HyDE（Hypothetical Document Embeddings，假想文档嵌入）

- **核心原理**：由学术界著名论文提出。由于“问题（Question）”和“答案文档（Document）”在表征空间上天然存在语义鸿沟（问句通常是疑问语气，文档是陈述语气），HyDE 让大模型先写一段假想的回答文档，然后**只对这个假想回答计算 Embedding 向量**去向量库检索。
- **解决痛点**：将“用问句找答句”转换成了“用（假想）答句找（真实）答句”，拉近了向量检索在空间中的分布距离。
- **代码实现**：使用 LangChain 的 `HypotheticalDocumentEmbedder` 与 `PromptTemplate`，把大模型生成的假想文本送入 Embedding 模型生成向量。

##### 3. 子问题查询（Sub-question Decomposition，复杂问题拆解）

- **核心原理**：当用户提问包含多个条件或跨越多个方面时，提示大模型将复杂长问题拆分为多个相互正交的子问题列表（Sub-questions），分别对各个子问题发起检索和问答，最后汇总。
- **解决痛点**：一次单点检索无法覆盖多意图、多跳转的复合问题（如“请假超过3天需要哪个领导审批，并且扣减多少绩效？”）。
- **代码实现**：编写了 `def sub_question(query)`，通过定制 Prompt 指导模型“创建子问题列表”，输出结构化子问题数组。

##### 4. 查询改写（Query Rewriting）

- **核心原理**：利用大模型将用户口语化、含糊不清的日常提问，转换并丰富为包含领域专业术语的正式表述。
- **解决痛点**：员工常说“我请个事假怎么扣钱”，而规章制度文档写的是“事假期间工资计算办法与考勤管理条例”，直接搜口语极易漏检。
- **代码实现**：在 `def question_rewrite(query)` 中，要求大模型从不同层次改写问题，并“在转述版本中增加规章制度的关键词”。

##### 5. 后退一步策略（Take Step Back / Step-back Prompting）

- **核心原理**：谷歌提出的一种经典检索策略。大模型面对具体案例时，先“后退一步”，将具体细节提炼为**更高维度的宏观概念或上位概念**进行检索。
- **解决痛点**：用户问“我爷爷去世了要回去几天？”，直接检索“爷爷”可能制度里根本没有这个词；后退一步抽象为“公司丧假的规定与直系亲属范围是什么？”，就能直接命中核心条款。
- **代码实现**：编写了 `def take_step_back(query)`，给大模型提供了 Few-shot 示例，将场景问题提炼成上位概念问题。

------

#### 二、 索引与存储端优化技术（MultiVectorRetriever 多索引检索）

传统 RAG 要求“存入向量库的切片”和“喂给大模型的上下文”必须是同一块文本。这导致了天然矛盾：切小了语义断裂缺上下文，切大了向量表征失真搜不准。代码中通过 `MultiVectorRetriever` 实现了**“检索索引”与“正文内容”解耦**的 3 种技术：

##### 6. 父子文档检索（Parent-Child / Small-to-Big Retrieval）

- **核心原理**：把原始大文档（父文档 Parent Chunk）存入外部存储（如 `InMemoryByteStore`）；同时将大文档切碎成很小粒度（如 100~200 字的小 Chunk）存入向量库。**检索时用小切片计算相似度，一旦命中，直接返回其对应的大父文档给大模型**。
- **解决痛点**：小切片检索定位极精准，大块父文档提供完整充沛的上下文，兼得两者之长。
- **代码实现**：通过 `MultiVectorRetriever(vectorstore=sm_chunk_db, byte_store=store, id_key="doc_id")` 实现自动映射回填。

##### 7. 文档摘要检索（Summary-based Retrieval）

- **核心原理**：大模型离线为每一个长文档/章节提炼一段高密度的主题摘要（Summary），将摘要生成向量存入向量库；检索时用用户问题与“摘要向量”匹配，命中后再召回完整长文本。
- **解决痛点**：长文本往往充斥着叙述性细节，导致整体向量偏离核心主题；摘要具备极高的语义纯度。
- **代码实现**：通过 LLM 生成 summary，将 summary 向量存入 `summary_chunk_db`，对应原文档存入 docstore。

##### 8. 假设性问题检索（Hypothetical Questions Retrieval）

- **核心原理**：离线阶段，利用大模型遍历文档，预先推演并生成“读者阅读该文档后可能会提出的 3~5 个问题”，将这批假设性问题向量化并建立索引；检索时用用户的实际提问去匹配这些假设性问题。
- **解决痛点**：实现“问句搜问句”，句式、语气与语义空间高度对称，匹配成功率远高于“问句搜正文陈述句”。
- **代码实现**：定义 Pydantic 类 `HypotheticalQuestions` 结构化提取问题，并绑定到 `hq_retriever`。

------

#### 三、 检索召回与排序技术

##### 9. 混合融合检索（Hybrid / Ensemble Retrieval：BM25 + 向量）

- **核心原理**：同时运行**稀疏检索（BM25 关键词精确匹配）\**与\**密集检索（Dense Embedding 语义相似度）**，然后通过加权算法（如 0.3 BM25 + 0.7 向量）将两路结果去重融合。
- **解决痛点**：单纯向量检索在处理专有名词、工号、政策条款编号、生僻缩写时经常“胡乱泛化”而漏掉精准词；BM25 能够保底字面精确匹配。
- **代码实现**：引入 `jieba` 分词定制中文分词器 `jieba_preprocessing_func`，构建 `BM25Retriever`，与向量检索器一同传入 `EnsembleRetriever`。

##### 10. Cross-Encoder 重排序（Rerank 模型精排）

- **核心原理**：向量召回是双塔结构（Query 和 Doc 分开编码，丢失了词与词的精细交叉注意力）。Rerank 则使用交叉编码器（Cross-Encoder，如 `bge-reranker-base`），将 `[Query, Document]` 作为一个整体输入模型，计算两者的深层注意力得分并重新排序。
- **解决痛点**：粗排召回的前 10~20 篇文档常含有“语义看似接近但关键事实完全相反”的假阳性文档，Rerank 能高精度滤除噪音，把最相关的 Top-3 挑出来。
- **代码实现**：加载 HuggingFace 的 `AutoModelForSequenceClassification` 和 `bge-reranker-base`，在 GPU 上对初筛候选对进行联合打分并截断。

------

#### 四、 流程控制与智能体（Agentic Loop）架构

##### 11. 迭代式检索增强生成（Iter-RetGen / Iterative RAG）

- **核心原理**：多轮交替循环。第 1 轮检索并生成一个粗糙答案；第 2 轮将“原问题 + 粗糙答案”作为更加丰满的线索再次检索，然后再生成最终答案。
- **解决痛点**：避免“一锤子买卖”，用中间推理出的答案引导下一轮更深层次的信息挖掘。
- **代码实现**：编写了 `def iter_retgen(query, iter_num=2)` 循环更新上下文。

##### 12. Self-RAG（基于 LangGraph 状态图的自反思与自我纠错）

- **核心原理**：不再是单向线性的 RAG，而是利用 **LangGraph 状态图（StateGraph）** 把检索、评估、改写、生成连接为一个有条件分支、可自我循环修正的智能体闭环。

- **解决痛点**：防止大模型在“检索结果很差”时强行作答造成幻觉；检索结果不合格时自动重试与改写。

- 代码实现包含的关键节点与逻辑

  ：

  1. `retrieve`：执行检索召回文档；
  2. `grade_documents`：大模型自动评估召回的文档与用户问题是否真正相关；
  3. `decide_to_generate`（条件分支）：若无相关文档，自动路由到 `transform_query2doc` 或 `transform_query_rewrite` 进行改写并重新检索；
  4. `generate`：生成答案；
  5. `grade_generation_v_documents_and_question`：评估生成的答案是否有文档事实依据（防幻觉），以及是否解答了用户问题；若不达标，再次触发改写循环。

from langchain.chains import HypotheticalDocumentEmbedder, LLMChain
from langchain.prompts import PromptTemplatefrom langchain.chains import HypotheticalDocumentEmbedder, LLMChain

def hyde(query, include_query=True):
    prompt_template = """你是一名公司员工制度的问答助手, 熟悉公司规章制度，请简短回答以下问题:
    Question: {question}
    Answer:"""
    
    prompt = PromptTemplate(input_variables=["question"], template=prompt_template)
    # llm_chain = LLMChain(llm=langchain_llm, prompt=prompt)
    # 关键修改：用 prompt | langchain_llm 替代 LLMChain
    llm_chain = prompt | langchain_llm

    embeddings = HypotheticalDocumentEmbedder(llm_chain=llm_chain,
                                base_embeddings=embedding)
    hyde_embeddings = embeddings.embed_query(query)
    
    if include_query:
        query_embeddings = embedding.embed_query(query)
        result = (np.array(query_embeddings) + np.array(hyde_embeddings)) / 2
        result = list(result)
    else:
        result = hyde_embeddings
    result = list(map(float, result))
    return result

> 用户的问题是：
> > **`"那个，我们公司有什么规定来着？"`**
>

>
> 1. **混合原始 Query 时（`include_query=True`）**：
>    * 原始 Query 过于口语和模糊，它的向量表征带有很强的模糊性与口语噪音。
>    * 当把它与 HyDE 向量按 `50% : 50%` 平均后，原本精准的伪文档向量被原始 Query 的口语噪音**向后拉偏**了。
>    * 导致最终只召回了一些边缘片段（如企业文化宣传语），缺少关于“公司制度概览”的核心条款。
>
> 2. **纯使用 HyDE 时（`include_query=False`）**：
>    * HyDE 的 Prompt 是：*“你是一名公司员工制度助手，请简短回答...”*。
>    * 大模型先脑补生成了一段规范的书面语伪文档（例如：*“公司制度包括考勤制度、请假制度、休假规定、违规违纪处理等...”*）。
>    * 纯用这段**书面化、充满规章制度专业词汇的假定文档**去匹配 Chroma 数据库中的真文档，实现了从 **`Query - Doc 匹配`** 到 **`Doc - Doc 匹配`** 的跨越。
>    * 因而精确命中了文档中写有 *“本制度包括了考勤、休假、加班等方面的规定”* 的**总述段落**（上下文2），让 RAG 最终成功回答。

> * **HyDE 的优势**：消除了“用户口语化提问”与“知识库书面语文档”之间的**表达鸿沟（Semantic Gap）**。
> * **何时混合 Query (`include_query=True`)**：
>   当用户问题中包含**非常明确的实体、型号、专有名词、特定人名**时，保留原 Query 向量能防止大模型“脑补伪文档”时产生幻觉偏离主题。

>   当用户提问**极度简短、口语化、含糊抽象**时（如本例），纯 HyDE 向量能过滤口语噪音，大幅提升文档召回质量。

> 你笔记本前面学过 `query2doc`，把它们放一起对比就会彻底清晰：
>
> | 检索方式           | 文本（Query）被改成什么样？                                  | 向量数据库实际用来比对的向量                                 |
> | :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **传统检索**       | `"那个，我们公司有什么规定来着？"`（没改）                   | `Embedding(原问题)`                                          |
> | **Query2Doc**      | **直接把文本拼长了**：<br>`"那个，我们公司有什么规定来着？，公司规定包括考勤、休假、加班..."` | `Embedding(拼接后的长文本)`                                  |
> | **HyDE (`False`)** | 文本没改，但生成了假想伪文档                                 | **`Embedding(假想伪文档)`**<br>*(完全用假想答案去搜真实答案)* |
> | **HyDE (`True`)**  | 文本没改，但生成了假想伪文档                                 | **`50% Embedding(原问题) + 50% Embedding(假想伪文档)`**<br>*(在向量空间里把两者融合)* |
>
> ### 总结
> * **Query 字符串本身没变**，用户问什么最后答什么；
> * `include_query=False` 相当于告诉向量数据库：**“别管用户问得多模糊口语，直接拿着大模型脑补的书面制度概要去库里捞书面文档”**；
> * `include_query=True` 相当于告诉向量数据库：**“既要参考大模型脑补的内容，也要兼顾用户原本口头提问的倾向”**。



#### 总结query2doc和HyDE

> ⭐**其实Query2Doc 与 HyDE都是在优化用户提问时的问题，对吗？**
>
> 
>
> **完全正确！你的理解一针见血。**
>
> 在 RAG 架构的分类中，**Query2Doc** 和 **HyDE** 都属于同一个技术分支：**“检索前查询增强与改写”（Pre-Retrieval / Query Transformation）**。
>
> 它们的本质目的完全相同，都是为了解决 RAG 检索中著名的 **“语义鸿沟”（Semantic Gap）**：
>
> ---
>
> ### 1. 它们试图解决的共同痛点
>
> 用户在提问时，经常存在两个天然问题：
> 1. **口语化与碎片化**：用户提问往往很短、很碎（比如 *“那个，怎么报销来着？”*）；
> 2. **提问与文档的表达不一致**：
>    * 用户输入的是**“疑问句”**（*“感冒发烧去出差怎么请假？”*）；
>    * 知识库里存的是**“陈述句/制度条款”**（*“第三节：教职工病假需在两个工作日内补办手续...”*）。
>
> 在传统的向量检索中，拿“短小的疑问句”去匹配“大篇幅的书面陈述句”，向量相似度往往很低。所以，它们都在**想办法把用户的提问“改写/扩写”成更像知识库文档的形式**。
>
> ---
>
> ### 2. 两者的实现手段有何不同？
>
> 虽然目标一致，但它们的**实现思路（路径）**不同：
>
> ```
>                     ┌─► Query2Doc:【文本拼接】──► 拼成更长的字符串 ──► 生成一个混合向量
>                     │
> 用户原始提问 ───────┤
>                     │
>                     └─► HyDE:     【向量对齐】──► 分别转成数学向量 ──► 在向量空间中融合
> ```
>
> | 对比维度     | **Query2Doc**                                                | **HyDE**                                                     |
> | :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **所属层面** | **文本级改写（Text-level）**                                 | **向量级对齐（Embedding-level）**                            |
> | **做法**     | 大模型生成补充信息后，**直接用字符串拼在原问题后面**：<br>`f"{query}, {doc_info}"` | 大模型生成伪文档后，**分别对原问题和伪文档算向量**，在数学空间里取平均或直接替换。 |
> | **核心哲学** | “既然原问题太短，我就多补点相关词和上下文，让字数变多、信息更丰富。” | “不要拿【问题】搜【答案】；先让大模型造个【假答案】，拿【假答案】搜【真答案】（Doc-Doc 匹配）。” |
>
> ---
>
> ### 3. 拓展：在整个 RAG 体系里的全貌
>
> 你在这一章学到的很多技巧，其实都是在**“优化用户问题”**这个预处理阶段发力：
>
> * **HyDE / Query2Doc**：把“口语提问”扩写成“书面伪文档”（解决口语与书面语的差异）；
> * **Query Rewrite（查询改写）**：去除多轮对话里的代词（比如把“它多少钱？”改写为“iPhone 15 多少钱？”）；
> * **Sub-Question（子问题拆解）**：把复杂的长问题拆成若干个简单小问题分别检索；
> * **Step-back Prompting（后退一步提问）**：把具体狭窄的问题提升到更高维度的概念去检索。
>
> 所以你的直觉非常准，不管是直接拼文字（Query2Doc）还是在向量层面做融合（HyDE），**都是在利用大模型给原始问题“加Buff”，让检索器更容易在知识库中搜中正确内容。**



> ⭐⭐**“生成一个混合向量”和“在向量空间中融合”的区别是什么？**
>
> 
>
> 这两个表述看似相似，但在计算机和数学底层，是 **两种完全不同的“融合阶段”与“融合方式”**：
>
> * **Query2Doc（“生成一个混合向量”）**：是 **先混文字，再算向量** —— 属于 **“早期融合（Early Fusion）”**。
> * **HyDE（“在向量空间中融合”）**：是 **先各自算向量，再在数学空间中叠加** —— 属于 **“晚期融合（Late Fusion）”**。
>
> 我们可以从以下三个维度彻底看清它们的区别：
>
> ---
>
> ### 1. 计算过程的区别（核心差别）
>
> #### ① Query2Doc（文本混合 ➔ 端到端生成向量）
> $$V = \text{Embedding}(\text{原问题} + \text{伪文档})$$
> * **过程**：先把原问题和伪文档用字符串硬拼成一段长文本：
>   `"那个，我们公司有什么规定来着？, 公司的规章制度包括..."`
> * 然后把这一整段长文本**一次性喂给 Embedding 模型**（通常是 Transformer 架构）。
> * 在模型内部，Transformer 的 **Self-Attention（自注意力机制）** 会让原问题的每一个字和伪文档的每一个字**进行深度的非线性交叉计算**，最后端到端输出**一个**全新的向量。
>
> #### ② HyDE（各自独立编码 ➔ 向量空间几何运算）
> $$V = \frac{\text{Embedding}(\text{原问题}) + \text{Embedding}(\text{伪文档})}{2}$$
> * **过程**：原问题和伪文档**互不见面、互不影响**。
> * 原问题单独进模型，算出一个坐标 $V_A$；
> * 伪文档单独进模型，算出一个坐标 $V_B$；
> * 最后在由几千个维度组成的高维几何空间（向量空间）中，通过纯粹的高中数学向量加法和标量除法，求出这两个坐标的**中点坐标**。
>
> ---
>
> ### 2. 生动比喻：做菜 vs 调鸡尾酒
>
> * **Query2Doc（先拼文本）** 就像 **把两种食材扔进搅拌机一起打碎烹饪**：
>   原问题和伪文档在模型内部充分发生了“化学反应”（自注意力计算），你很难再单独把原问题剥离出来。
> * **HyDE（空间融合）** 就像 **调鸡尾酒**：
>   原问题是一杯伏特加，伪文档是一杯果汁，它们各自是独立的成品，最后在杯子里按照 50% : 50% 的比例混合在一起。
>
> ---
>
> ### 3. 工程与效果上的优缺点对比
>
> | 对比维度         | **Query2Doc（文本拼接后生成）**                              | **HyDE（向量空间数学融合）**                                 |
> | :--------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **融合层级**     | 语义/词汇层级的非线性融合                                    | 几何/空间层级的线性插值                                      |
> | **权重的可控性** | **不可控**。<br>原问题短、伪文档长，拼在一起时长文本往往会“反客为主”，把短问题的注意力稀释淹没。 | **完全自由可控**。<br>可以用数学公式精准调整比例：<br>$V = \alpha V_{原问题} + (1-\alpha) V_{伪文档}$<br>比如让原问题占 20%，伪文档占 80%，或者像你刚才那样把原问题设为 0%（`include_query=False`）。 |
> | **独立性**       | 原问题和扩写文本强绑定在一起。                               | 两者解耦。你可以只用伪文档，也可以缓存原问题向量，灵活性极高。 |
>
> ### 总结
> * **“生成一个混合向量”** 是在**输入端（文字端）**做加法，交给神经网络去消化；
> * **“在向量空间中融合”** 是在**输出端（坐标端）**做数学加法，由你用数学公式完全掌控两个语义所占的权重比例。

> ⭐⭐**“查询改写”是什么检索增强技术？**
>
> 
>
> 在检索增强生成（RAG）系统中，**“查询改写”（Query Rewriting）**属于 **检索前阶段（Pre-Retrieval）** 的核心优化技术，通常也被统称为 **查询转换（Query Transformation）**。
>
> ---
>
> ### 一、 核心定义与定位
>
> * **所属阶段**：**Pre-Retrieval（检索前增强）**
> * **核心目的**：在用户问题进入检索器（向量检索 / BM25 稀疏检索 / 混合检索）之前，利用大模型（LLM）等能力，将用户的原始问题**重新组织、规范化或扩充**，生成一个或多个**更利于知识库检索**的 Query。
>
> ---
>
> ### 二、 解决的核心痛点
>
> 在真实的 RAG 系统中，用户直接输入的问题往往不适合直接检索，查询改写主要解决以下 3 个问题：
>
> 1. **词汇/语义鸿沟（Vocabulary Mismatch & Semantic Gap）**：
>    * 用户习惯用**生活化、口语化**语言表达（如：“*临时外出需要怎么申请*”）；
>    * 知识库/制度文档通常用**书面化、规范化、专业术语**书写（如：“*考勤管理办法*”、“*因公外出审批流程*”、“*打卡报备规程*”）。
>    * 如果直接做 BM25 或向量检索，命中精度和召回率通常较低。
> 2. **意图模糊与信息缺失**：
>    * 用户问题常包含客套话（“*我想了解下...*”）、模糊代词（“*那个怎么弄*”），改写可以过滤噪音、提炼核心意图。
> 3. **缺少领域上下文**：
>    * 将通用问题置于特定业务场景（如你的代码中指定的“*公司员工规章制度*”）下，补充领域专有名词。
>
> ---
>
> ### 三、 结合你代码的分析
>
> 在你的代码中：

> prompt_template = """你是一名公司员工制度的问答助手, 熟悉公司规章制度。

> ### 四、 RAG 中常见的查询改写/转换模式
>
> 除了代码中的**单句关键词增强**，在进阶 RAG 体系中，查询改写技术还包含以下几种常见形态：
>
> | 技术名称                                    | 工作原理                                                     | 适用场景                                                     |
> | :------------------------------------------ | :----------------------------------------------------------- | :----------------------------------------------------------- |
> | **多查询扩展 (Multi-Query)**                | 让 LLM 从不同角度生成 3~5 个等价或互补的 Query 分别检索，最后去重合并 | 提高**召回率（Recall）**，避免单次检索由于措辞偏差遗漏关键内容 |
> | **RAG-Fusion**                              | 在 Multi-Query 的基础上，对多个检索结果列表使用倒数排名融合（RRF）加权排序 | 兼顾**召回率**与**排序相关性**                               |
> | **假设性文档嵌入 (HyDE)**                   | 先让 LLM 根据提问生成一篇“虚构但格式符合的假答案”，再拿假答案的向量去检索真实知识库 | 适合**文档很长、提问很短**，直接提问无法匹配语义的场景       |
> | **子问题分解 (Sub-Question Decomposition)** | 将复杂问题拆解为多个步骤/子问题（如：“*对比 A 和 B 部门的外出流程*” $\rightarrow$ “*A 部门外出流程*” + “*B 部门外出流程*”） | 复杂多跳（Multi-Hop）查询                                    |
> | **回退提问 (Step-Back Prompting)**          | 从具体问题提炼出一个更高级别、更抽象的概念问题先检索背景知识 | 涉及底层原理、规章框架层面的问题检索                         |
>

### 三、 逐段代码拆解分析

#### 1. 灵活的分支检索（多策略兼容设计）
```python
if context_query_type == "vector":
    related_docs = zhidu_db.similarity_search_by_vector(context_query, k=k)
elif context_query_type == "query":
    related_docs = zhidu_db.similarity_search(context_query, k=k)
elif context_query_type == "doc":
    related_docs = context_query
else:
    related_docs = zhidu_db.similarity_search(context_query, k=k)
```
这里是该函数最精妙的设计点：
- **`"query"`（普通文本检索）**：传入的是文本（如原始问题、改写后的问题、或者拼接了伪文档的 Query2Doc），Chroma 会自动将其先`转换为 Embedding`，再去计算向量相似度。
- **`"vector"`（向量直接检索）**：传入的直接是一个 Embedding 向量。常用于 **HyDE（假设文档嵌入）** 技术——先让大模型生成一篇虚构答案，并提前提取出向量，直接送入向量库做相似度计算。
- **`"doc"`（绕过检索）**：直接传入预处理好的文档列表。常用于 **Rerank（重排序）** 或多路召回融合后，文档已经挑选好了，直接送进流水线组装回答即可。

#### 2. 上下文组装与打印调试
```python
context = "\n".join([f"上下文{i+1}: {doc.page_content} \n" 
                     for i, doc in enumerate(related_docs)])

print(f"context: {context}")
```
- 将召回的多个文档切片（`Document`）的文本内容提取出来，加上序号（`上下文1:`、`上下文2:`）格式化拼接。
- 显式打印 `query` 和 `context`，方便开发者直观看到：**到底检索到了哪些内容、有没有召回有效制度，还是检索到了无关噪音**。

#### 3. 提示词（Prompt）格式化
```python
prompt = PromptTemplate(
            input_variables=["question", "context"],
            template=prompt_template)
llm_prompt = prompt.format(question=query, context=context)
```
- 利用 LangChain 的 `PromptTemplate`，将真实的原始问题 `query` 和刚才检索到的 `context` 注入模板，构成送给大模型的完整指令。

#### 4. 大模型生成（支持流式）
```python
if stream:
    response = llm(llm_prompt, stream=True)
    print(f"response: ")
    for chunk in response:
        content = chunk.choices[0].delta.content or ""
        print(content, end='', flush=True)
    return ""
else:
    response = llm(llm_prompt, stream=False, temperature=temperature)
    return response
```
- **流式（Stream=True）**：调用 LLM 接口逐 chunk 读取大模型生成的内容，使用 `flush=True` 在控制台实现打字机效果，大幅降低用户的首字等待感知。
- **非流式（Stream=False）**：等待模型完全生成后，将完整字符串返回给外部调用方（通常用于自动化评估、批量评测等场景）。

### 四、 总结：为什么要将 `query` 和 `context_query` 分开？

这个函数之所以将 **`query`（提问）** 和 **`context_query`（检索词）** 拆成两个入参，核心是为了支持 **Query-Driven 的高级 RAG 优化算法**：
1. **普通 RAG**：`run_rag_pipline(query, query)`（提问什么就去搜什么）；
2. **Query2Doc**：`run_rag_pipline(query, query2doc(query))`（用扩展后的伪文档去搜真实文档，但最终仍回答用户的原始问题）；
3. **HyDE**：`run_rag_pipline(query, doc_embedding, context_query_type="vector")`（用假设文档的向量去搜，但最终仍回答原始问题）。
